# Enigma-desktop 创新与模型协作分析报告

2026-10-25，Asia/Shanghai。评估基线：Hana 0.450.0、Pi 1.4.0、迁入的 Enigma-next 0.4.2 工程模块。本报告汇总本轮新增的模型职责拆分、运行中切换，以及此前仅要求研究的记忆、托管、减少返工、文档专精等议题。**报告中的候选方案没有作为新功能实现；迁入的现有基础能力另列。**

## 1. 研究结论与证据范围

建议产品方向保持为个人多仓库 coding agent，优先特化“跨仓库迁移与可验证文档维护”。模型协作先探索一个主执行循环上的可选路由：简单任务单模型；复杂任务按需规划；出现真实困难后升级；实际检查负责验收。固定的 Kimi 规划、DeepSeek Flash 编码是可测试的配置，而不是已证明最优的默认组合。

Pi 1.4.0 已有公开 virtual model 扩展，能在每次请求前选择物理模型与思考级别，保存分支路由状态，并记录实际回答模型。官方示例甚至已有强模型先规划和首次编辑、随后切换较便宜模型的做法。这两个新点子应基于现成接口增加工程语义与易用界面，核心路由本身不宜宣传为原创。[Pi virtual models](https://github.com/earendil-works/pi/blob/v1.4.0/packages/coding-agent/docs/virtual-models.md)

RouteLLM 研究请求发出前的模型选择，FrugalGPT 研究模型级联；DeepSeek 官方支持同一模型的思考模式和力度控制。这些相互独立的来源支持“有多种分配计算的方法”，不能共同证明某个品牌适合某个职责，也不能将问答基准的节约比例直接应用到多轮代码改造。[RouteLLM](https://arxiv.org/abs/2406.18665)、[FrugalGPT](https://arxiv.org/abs/2305.05176)、[DeepSeek thinking mode](https://api-docs.deepseek.com/guides/thinking_mode/)

证据标签采用以下口径：Pi 接口属于**官方单源事实，并与本地固定版本源码核对**；跨方案取舍属于**设计判断**；Enigma 的收益属于**待实测**。本轮没有 Kimi／DeepSeek 配对实验，没有测得提速或成本收益，没有建立路由分类器。公开资料也不能证明下文点子从未在其他 Agent 出现。

## 2. 全部议题与实现状态

| 议题 | 当前基础 | 尚待研究或实现的增量 | 建议 |
|---|---|---|---|
| 多仓库协同 | 仓库注册、依赖、原联合检查、隔离任务与方案 | 契约变化驱动任务拆分，先验证最难的联动假设 | 继续作为主方向 |
| 时光机 | 会话树关联代码检查点、恢复、独立 worktree 方案 | 跨回溯失败条件、模型路线比较、依赖范围恢复 | 重点研究 |
| 计划、进度、独立验收、中断恢复 | 现有工程模块已有 | 压缩后约束对账、可接管的最小下一步、验收债务 | 保留，合并呈现，避免多套重叠工作流 |
| 权限与脱敏、按需审查 | 现有工程和宿主边界已有 | 模型路由权限继承、恢复后独立核对 | 保留；不靠换模型绕过审批 |
| 轻量记忆与中文召回 | 来源、范围、版本、纠正/忘记、按需读取 | 按真实复用价值整理、跨仓契约联动、冲突解释 | 基础保留；自动整理默认后置 |
| 做梦／空闲计算 | 有界草稿整理，不调用模型 | 可暂停的模型整理、效用反馈、总成本核算 | 先试验，暂不常驻 |
| 运行观察与“为什么慢” | 独立状态读取、阶段与证据、按需解释 | 等待关系、请求时延分解、切模过程可见性 | 保留并增强 |
| 托管管家 | 观察旁路可复用 | 独立监护进程、有界恢复、隔离维修 | 分级研究；未实现自动托管 |
| 新背景会话与跨 Agent 交接 | Pi 分支与 Markdown/JSON 包、目标适配 | 差量交接、接收端主动补读、背景模板 | 基础保留，扩展按实际目标逐个验收 |
| 技能、任务配方、项目资料、版本产物、服务与后台 | 已有工程能力迁入 | 从成功任务提出可编辑流程，过期步骤自动待验 | 保留常用入口，低频动作收起 |
| 发起对话时分配模型 | 宿主已有模型/思考设置 | 规划、执行、可选复核模型配置及预算 | 新研究，优先小试验 |
| Loop 运行中切模型 | Pi 底层接口已有 | 待切换状态、下一请求生效、兼容与费用显示 | 新研究，优先实现候选 |
| 文档专精 | 来源阅读、材料、实际验证、版本产物 | 声明来源、可执行示例、跨文档一致性维护 | 优先专精候选 |
| 桌面系统操作专精 | Hana 宿主有相关通用能力 | 系统效果建模、撤销与可靠验收 | 后置，当前不扩展权限范围 |
| 更换 DSH 宿主 | 已有历史比较研究 | 只有出现明确接口缺口时做局部适配试验 | 本轮不再次迁移宿主 |

“已迁入”表示实现和接口基础存在，不等于每种业务场景、平台或 provider 全部验证。当前桌面迁移的执行验收与已知缺口见[迁移记录](enigma-migration-progress.md)。此前报告里的旧测试数量与“待实现”章节是历史时点，不应拿来替代当前状态。

## 3. 模型职责拆分

### 3.1 可选拆法

| 拆法 | 适用场景 | 主要收益假设 | 代价与失败方式 |
|---|---|---|---|
| 单模型，调整思考力度 | 大量日常小改动 | 减少角色交接和缓存损失 | 力度选错仍浪费；参数跨 provider 含义不同 |
| 强模型规划，快速模型执行 | 多仓接口升级、复杂约束 | 一次明确方案后低成本推进 | 计划错误会被放大；执行仍需要判断能力 |
| 强模型先完成难点，再交给快速模型 | 架构入口不确定或工具策略复杂 | 先用真实代码/实验证明路线，再交接重复步骤 | 切换时机不能只按“已经调用 write 工具”判断 |
| 普通模型主执行，困难时升级 | 简单与复杂步骤混合 | 避免每个任务支付完整规划成本 | 廉价失败后返工更贵；不能只凭模型自信度升级 |
| 主执行＋按需独立复核 | 大改、迁移风险、交付前争议 | 用不同证据视角找遗漏 | 两个模型可能共同误判；仍需真实原验收 |
| 独立只读规划会话＋主执行会话 | 需要隔离规划与代码权限 | 规划能比较假设，主会话有明确执行契约 | 额外延迟、背景重复、计划与当前代码漂移 |

建议先做“可配置阶段＋有证据的升级”，保留单模型作为默认和对照。独立规划会话只用于复杂目标，避免每个小编辑都经过多人流水线。路由方法可借鉴公开研究，但多轮任务中的返工、工具效果和上下文缓存属于额外评估对象。[RouteLLM](https://arxiv.org/abs/2406.18665)、[FrugalGPT](https://arxiv.org/abs/2305.05176)

### 3.2 规划的输出与权限

规划输出应是一份短的、可核对的执行约定：目标、原要求来源、受影响仓库、已确认事实、未确认前提、步骤依赖、原检查、禁止动作、何时回到规划。它不是隐含思维链，也不是一份不可修改的大作文。执行模型可以提出修订；有证据表明计划假设失效时，暂停受影响步骤重新规划，不能机械执行错误方案。

规划阶段是否只读，由宿主工具与文件/进程边界执行；模型名字或角色提示不能形成权限隔离。必要的探索实验应单独授予明确范围。规划可以推荐验收步骤，不能删改用户或项目原成功标准。独立复核模型只能补充发现，不能以“认可”替代真实验收。

推荐的配置界面只保留：执行模型、可选规划模型、可选复核模型、各自思考力度、总预算。规划和复核默认沿用执行模型；只有用户配置差异才展示更多字段。Kimi＋DeepSeek Flash 作为可选预设，名称使用当前 provider 目录中的精确 ID，缺配置时解释缺口。普通任务不应自动加载三份模型上下文。

### 3.3 更值得探索的拆分单位

比“Plan 全归 Kimi、所有代码全归 Flash”更细的拆分是按**不确定性和影响范围**分配计算：找错入口、协议歧义和跨仓契约决策值得较强推理；已证实接口下的重复修改、格式调整和材料整理可以采用快速模型。验证失败若指向方案前提，就回规划；若是确定的局部错误，就留在执行阶段修复。

另一个轻量选项是先保持同一模型，调整思考力度。DeepSeek 官方有思考模式与力度参数；这证明接口可配置，不证明其每种力度在本项目的质量或时延。必须将模型、API 协议与实际参数共同记录，不能把所有 provider 的 low/high 当成等价计算量。[DeepSeek thinking mode](https://api-docs.deepseek.com/guides/thinking_mode/)

## 4. Agent Loop 运行中切换模型

### 4.1 可以实现的时点

| 当前状态 | 建议用户行为 | 实际生效时点 |
|---|---|---|
| 等待或接收一个模型回答 | 选择模型，显示“当前请求用 A，下一请求用 B” | 当前完整回答及其工具调用结算后，下一次模型请求 |
| 工具或长验证执行中 | 提交待切换模型 | 保留本次工具执行，下一模型请求读取实际结果 |
| 正在压缩 | 保存待切换意图，不并发修改压缩流程 | 当前压缩结算，再进行兼容核对 |
| 两次模型请求之间 | 核对授权/能力后直接采用新选择 | 下一请求 |
| 希望立刻停止当前生成 | 明确取消当前请求并选择模型 | 确认取消及可能效果后重新发起，属于中断恢复 |
| 已有回答与工具执行完成，Loop 即将结束 | 保存选择 | 下一次用户消息；不为了切模制造额外回合 |

已有网络请求绑定原模型，不能把半条 token 流无缝改成另一个模型继续生成。**无需停止整个任务的可行版本，是保持会话、工具效果和运行身份，在下一次模型请求前切换。**这是对实际请求生命周期的设计判断，与 Pi 的 request preparation 和 virtual model 接口相符。[Pi AgentSession](https://github.com/earendil-works/pi/blob/v1.4.0/packages/coding-agent/src/core/agent-session.ts)、[Pi virtual models](https://github.com/earendil-works/pi/blob/v1.4.0/packages/coding-agent/docs/virtual-models.md)

### 4.2 适配位置

优先用 `pi.registerVirtualModel()` 建立可选路由配置，通过 `route(request, ctx)` 在下一请求读取阶段、已验证难点、待切换选择与当前权限。Pi 已区分 `user`、`continuation`、`retry` 和 `direct`，保存虚拟选择与实际模型，并将路由状态保存在会话分支；无需改 Pi 内核。[Pi virtual models](https://github.com/earendil-works/pi/blob/v1.4.0/packages/coding-agent/docs/virtual-models.md)

本仓 `core/session-coordinator.ts` 已有普通 `switchSessionModel()`，会检查压缩和上下文大小并调用 `session.setModel()`。这说明不用重建主循环；但它没有本报告所需的待切换协议、阶段路由、完整状态显示及混合 provider 验收。因此**不能把现有模型菜单宣称成已经完成热切换产品功能**。新增适配应维护 Hana 元数据、缓存契约与使用量投影，不能在插件里偷偷改模型而让宿主继续显示旧信息。

阶段推进需引用已提交的工具/检查证据，不能在路由器“决定派发”时就标成“规划完成”或“编码成功”。Pi 的路由状态可以在请求发送前保存且在请求失败后仍留下，`direct` 请求又不保存这类状态；压缩、旁路说明和独立审查应使用各自明确配置，避免误触发执行阶段的模型升级。[Pi virtual models](https://github.com/earendil-works/pi/blob/v1.4.0/packages/coding-agent/docs/virtual-models.md)

### 4.3 必须处理的边界

1. **完整工具调用与实际效果。** 半条 JSON 工具调用不执行；当前已派发操作不能因为切模再次重放。未确定终态的写入不能假装取消成功。
2. **跨模型历史兼容。** 文本、图像、工具 schema、tool-call ID、签名推理与 provider 专用字段不同。Pi 有消息转换机制，但仍需实际双向验证；无法合法转移的签名/内部状态不能伪造。
3. **思考与工具协议。** DeepSeek 的 thinking 工具交互对 `reasoning_content` 有专门回传规则；不能对所有模型一律丢掉或一律跨 provider 回传该字段。[官方说明](https://api-docs.deepseek.com/guides/thinking_mode/)
4. **上下文与缓存。** 目标模型容量更小可能需要压缩。Pi 官方明确提醒跨模型切换影响提示缓存，并示范在工具后续请求保持同模型；频繁来回切换可能增加成本与首 token 等待。[Pi virtual models](https://github.com/earendil-works/pi/blob/v1.4.0/packages/coding-agent/docs/virtual-models.md)
5. **凭证和范围。** 仅选择已配置、允许用于本任务的 provider；更换模型不增加工具、目录或联网权限，不自动把私有资料发给未授权服务。
6. **并发与恢复。** 待切换选择附带会话 ID、运行代次、修订号和请求边界；用户反复选择时旧请求不能覆盖新选择。时光机恢复旧模型路线后，最新明确偏好、可用配置、删除和权限仍优先。
7. **失败与预算。** 升级次数和重试都有上限；限流可更换已配置后端，验收方法错误不能靠换模型无限重试。不同模型的 token、实际费用或未知费用分别记录，Gateway 可见数据不能冒充供应商账单。

## 5. 记忆、做梦与跨仓库知识

基础路线保持小型、可回查、可纠正的记忆：项目事实、跨仓契约、任务决策、带条件的排障经验和显式个人偏好。检索先给短摘要与来源入口，正文按需读。版本、权限、删除和当前用户要求决定是否可用，不把记忆提升成系统指令。

ReasoningBank 将成功与失败轨迹形成可检索经验，MemRL 探索结合相关性与效用信号，ACE 讨论增量维护而非反复重写整份上下文。这些研究提供机制依据，适用任务、反馈来源与成本不同；Enigma 更适合先用真实原检查和来源版本给经验附条件，不立即建设训练或强化学习系统。[ReasoningBank](https://arxiv.org/abs/2509.25140)、[MemRL](https://arxiv.org/abs/2601.03192)、[ACE](https://arxiv.org/abs/2510.04618)

跨仓库增量是保存关系和适用条件：接口生产方、SDK、消费者、共同检查、版本兼容约定；上游源码变化使依赖结论重新待验。相互矛盾的经验同时保留来源和条件，不能只用较新的总结覆盖旧事实。分支探索中的临时判断先留在任务范围，有真实跨任务复用后再提出项目记忆草稿。

做梦候选不采用整夜反复总结所有会话。只整理近期可能复用、含新证据、值得付出成本的少量草稿；主任务恢复时让路；按来源修订合并，拒绝旧快照覆盖新纠正。Sleep-time Compute 研究问题到来前的上下文预计算，不能据此前台更快就断言总成本更低。现有 Enigma 小样本对照也没有显示轻量记忆更快，应保留无记忆和直接查原历史的对照。[Sleep-time Compute](https://arxiv.org/abs/2504.13171)、[本项目记忆对照](../packages/enigma-engineering/docs/memory-comparison.md)

## 6. 时光机与减少返工的新机制

关于“Kimi 最新取消时光机”：本轮核对的官方 PR #2055 是将 undo 调整为领域负责，并协调 Todo、Plan 和任务通知状态；它不是“已永久移除撤销”的证据，也没有解释某个 UI 入口消失的原因。可以确认的风险是：只退聊天，其他任务状态会漂移；运行中撤销还需明确 admission 边界。[Kimi 官方 PR](https://github.com/MoonshotAI/kimi-code/pull/2055)

Claude Code 检查点和 LangGraph 时间回溯也有文件归属、覆盖范围与重执行边界。代码、会话投影、计划、验证、外部效果不能视为一个全能撤销动作；外部通知、发布和已发生的远端写入需要分别处理。[Claude checkpoints](https://code.claude.com/docs/en/checkpointing)、[LangGraph time travel](https://docs.langchain.com/oss/python/langgraph/use-time-travel)

| 点子 | 现实问题 | 拟议动作 | 可否定的反例与验收 |
|---|---|---|---|
| 关键假设先证伪 | 改完才发现入口/协议猜错 | 先找能区分方案的最小真实实验，绑定版本 | 小实验绕过集成难点；核算前置成本和最终返工 |
| 回溯留下失败条件 | 回退后又走同一失败路线 | 代码退回，保留版本、配置、错误、解除条件 | 临时断网不能永久封禁方法；条件改变可重试 |
| 方案只先比较难点 | 两套完整方案都写，浪费很大 | 同起点、同原标准，先做各自最不确定部分 | 局部成功不能冒充完整联动通过 |
| 压缩与交接要求对账 | 忘掉不可修改和必须验的要求 | 核对原用户来源、最新更新、未验项和效果 | 摘要不能反向改原要求；注入遗漏必须发现 |
| 等待前准备终态渠道 | 操作发起后永远查不到结果 | 预先明确 run ID、查询源和备用取证 | 通知成功不等于本次任务成功 |
| 保留标准的分层验证 | 大验证迟迟不给反馈 | 先跑揭错能力高的局部检查，保留原完整验收 | 原检查不得被删除；比较总耗时和漏项 |
| 完成凭据与验收债务 | 上个 Agent 说通过，下个直接相信 | 要求→当前版本证据→未知项，变更后失效 | 旧证据不得认证新代码；导出可逐项回查 |
| 事实到期复验 | 昨天可用的工具/服务今天变了 | 按变更条件复验相关结论 | 区分临时失联与事实改变 |
| 中断后的最小下一步 | 隔天回来不知道继续什么 | 展示目标、最后证据、未解假设和下一动作 | 先核对当前环境，旧摘要不能当现状 |
| 模型路线与代码方案一起比较 | 不知道强模型是否值得成本 | 同一节点分支试不同策略，保留相同原检查 | 小样本随机差异不称普遍胜负，计入所有失败调用 |
| 按依赖恢复最少状态 | 验证器坏了却全回滚代码 | 分层恢复展示、请求、工具、上下文或代码 | 依赖漏边会导致跨仓不一致；后置高成本试验 |

第一组优先候选是关键假设小实验、带条件的失败记录、完成凭据。它们单独也有使用价值，不要求每轮反思或常驻另一个模型。与 ACE、Reflexion 等反馈经验机制相邻，增量假设在于和源码版本、跨仓原检查、回溯分支结合；尚无本项目对照结果。[ACE](https://arxiv.org/abs/2510.04618)、[Reflexion](https://arxiv.org/abs/2303.11366)

## 7. 运行观察、慢任务与托管管家

观察需要分别回答：在做什么、执行是否仍存在、是否产生有依据的推进。静默、CPU 或 token 增长都不能单独判死活与价值。可扩展等待关系：主任务等审批、子任务等检查、模型请求等服务、显示等事件；给出来源和观测新鲜度，没有服务端遥测时不猜模型排队或隐藏推理。

慢运行优化先减少已测得的重复工作：相同版本的源码/索引/快照复用，有效原验收复用，按明确依赖增量读取，独立读取有界并行。超长验证先提供局部反馈和可靠终态渠道，再决定方法是否合理；不能仅因为耗时长就否定方法或自动放宽标准。切模型只可能缓解模型阶段，不能解决编译、I/O、浏览器展示或死锁。

托管建议采用独立进程：本地规则持续读取有界事实，模型仅在异常时辅助诊断。与主循环在同一进程的“观察线程”可能一起受事件循环阻塞；另一个模型还可能与主模型共享限额。Wink 提供异步行为纠偏研究，LangGraph 提供持久执行机制，Kimi 的 undo 强调状态协调；它们覆盖不同层，不能据此宣称主进程任意故障都可自救。[Wink](https://arxiv.org/abs/2602.17037)、[LangGraph durable execution](https://docs.langchain.com/oss/python/langgraph/durable-execution)、[Kimi undo](https://github.com/MoonshotAI/kimi-code/pull/2055)

| 托管等级 | 拟议权限与动作 | 要求 |
|---|---|---|
| 观察与影子建议 | 解释状态，提出可能恢复方法 | 先测正常静默任务的误报；不修改主任务 |
| 有界运行恢复 | 已授权的取消、重连、有限重试/重建 | 确认旧执行终态，独立预算，未知效果不重放 |
| 方案恢复 | 准备或执行已授权的检查点恢复 | 保留用户改动、原要求、失败条件和原验收；不能凭超时全回滚 |
| 隔离维修 | 新工作区修采集/通知/压缩适配组件，再验证切换 | 故障回归、版本替换和回退；不热改任意 live 内核，不自行扩权 |

压缩卡住先区分请求没完成、摘要已提交但投影坏了、仅页面没刷新。相应恢复请求、会话或展示；源码可能完全无需退回。无法获知某验证状态时，可以补查询/通知适配器，但必须取得本次真实终态；补了通知不算完成验证。干预后检查原故障、原目标与新副作用，不能只测重启率。

## 8. 文档专精与通用交接

文档方向建议特化可执行工程文档：跨仓 API/SDK 迁移指南、安装说明、技术设计/ADR、排障手册和需求验收。文档声明关联源码/Schema/用户决定/实验；源码可以证明行为，不能自动证明设计动机。来源变化后只重验受影响声明和示例，历史 v1/v2 章节要保留各自适用范围。

Diátaxis 可帮助区分教程、操作指南、参考与解释；doctest 与 Sphinx 可复用示例检查/参考生成。生成、导出或单个示例通过都不等于完整读者任务完成。插件增量是来源声明、跨文档冲突、当前代码对应版本及可复现迁移步骤，不再造文档编译器。[Diátaxis](https://diataxis.fr/)、[doctest](https://docs.python.org/3/library/doctest.html)、[Sphinx autodoc](https://www.sphinx-doc.org/en/master/usage/extensions/autodoc.html)

跨 Agent 交接保持宿主无关的背景包：共同背景、当前新目标、现行要求、代码位置/版本、证据、未确定事项。下一步研究差量交接，让接收端按问题补读；模型拆分也复用同一执行约定。支持文本包不等于支持任意 Agent 私有会话无损迁移，导入的工具结果不能伪装成接收端已执行事实。原生 fork 与代码 worktree 的写入协调继续分开处理。


## 9. 后续试验与优先级

| 顺序 | 最小试验 | 成功与失败都记录什么 |
|---|---|---|
| 1 | 手动下一请求切模＋可选阶段路由 | 中途无需重发目标，工具恰好执行一次，原要求/检查保持；不兼容切换可解释 |
| 2 | 单模型、思考力度、固定规划/执行、困难升级对照 | 同真实任务和原检查；全程时间、调用成本、失败返工、人工介入；没有显著收益就不默认启用 |
| 3 | 关键假设实验、失败条件和完成凭据 | 对错误前提的发现、重复失败、错拦，以及原联合验收 |
| 4 | 三仓 API 迁移文档维护 | 独立按文档完成升级；过期字段/命令被发现，设计理由有来源 |
| 5 | 管家影子建议与有界恢复 | 正常长任务误杀、请求/压缩故障、PID 重用、旧事件、双监护竞争、用户接管与重复副作用 |
| 6 | 按复用价值的空闲整理和差量交接 | 连续任务真实召回/采纳/纠正，总成本、陈旧知识使用和遗漏约束 |

模型试验须包括两种切换方向、工具调用后续、目标上下文更小、图像不兼容、限流、认证失效、压缩同时发生、取消、重启、分支恢复、连续修改选择和其他扩展共存。真实 provider 结果与受控故障测试分别呈现，不能拿受控返回当 Kimi/DeepSeek 联调。

不建议当前加入：每轮全量反思、永远三模型流水线、无限做梦、超时自动全回滚、无证据换验收标准、热修改任意内核、泛化全系统知识图谱或再次整体迁移宿主。它们增加的边界和维护负担暂未由收益支持。

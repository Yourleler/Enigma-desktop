# Enigma-desktop：现状、下一阶段与创新路线

更新：2026-10-25。代码基线：`8cf2b6b8`，开发分支 `codex/engineering-migration`，[草稿 PR #1](https://github.com/Yourleler/Enigma-desktop/pull/1)。本文给出后续规划；其中新增能力仍处于方案阶段。

## 1. 当前项目处于什么阶段

**Enigma-desktop 已成为可运行的 Mac 工程 Agent 开发版。下一阶段的重点，是把已有多仓能力组织成顺手的任务流程，再增加模型调度与可靠恢复。**

底层继续使用 Pi 1.4.0，桌面/Web 界面依托 Hana 0.450.0。Enigma-next 的工程模块已迁入，通过插件接到 Hana 的同一个主会话，模型、审批、压缩和会话资源由宿主管理。当前可用入口是 `npm run enigma:web`；`npm run enigma:open` 自动完成本机浏览器登录，默认头像也已替换。原 Enigma 和 Enigma-next 保留。

| 现有部分 | 当前已做到 | 下一步要补的实际缺口 |
|---|---|---|
| 多仓库工作 | 注册多个仓库、声明职责/依赖、改代码、运行联合检查、隔离子任务和合并 | 将这些入口串成一项任务，直接说明应改哪些仓库、还等什么、哪里未验 |
| 代码理解 | TS/JS/Python/Go、Schema 阅读，源码锚点、版本化结果、按任务/diff 的地图 | 工作台优先呈现问题相关的阅读路径和影响关系；“代码”主视图目前主要是文件树 |
| 计划与验收 | 按会话独立计划、原要求、检查证据与失效保护 | 统一展示目标、进度、阻塞和当前验收缺口，减少在多个面板之间查找 |
| 时光机 | 会话分支、代码检查点、受保护恢复、独立 worktree 方案；恢复保留最新要求与累计调用 | 补上“为什么放弃这条路线”和恢复后明确的下一步 |
| 记忆与背景复用 | 可选轻量记忆、中文召回、来源/范围/版本、纠正忘记；新背景会话和 Pi/Codex 交接 | 提高跨仓契约与失败经验的实际复用，缩短背景交接 |
| 运行状态 | 旁路读取阶段、进程和证据，可回答为什么慢；后台任务可等待/取消 | 把等待对象和最近有意义的进展讲清楚；自动监护恢复尚未实现 |
| 图形工作台 | 原生 React、持久标签、源码/资料/产物预览、玻璃与动效、窄窗回退 | 部分领域详情仍是通用证据视图；正式应用标识、安装器、更新源与生产签名待收尾 |
| 模型设置 | 已接通 Gateway，已有模型和思考力度选择 | 运行时模型菜单仍拦截切换；没有规划/执行模型配置或自动阶段路由 |

这里最需要区分的是**工程接口可用**与**日常操作已经顺手**。三仓修改、联合验收、恢复、fork、审批取消及打包运行有实际验证；68 个表单的覆盖说明入口存在，不能替代真实任务体验。完整回归及两个已知上游发布测试失败见[迁移验收记录](enigma-migration-progress.md)。最新登录/头像改动另完成了相关回归，未把前一提交的全量数字称为新提交全量复验。

## 2. 产品方向与已有功能的取舍

### 2.1 主方向：个人多仓库改造助手

重点解决一类完整工作：**理解多个仓库的联系，完成联动改造，验证整个链路，并在走歪或中断后继续。**典型场景是服务接口、SDK、调用方与文档同时升级。多仓协同、代码阅读、时光机和项目记忆围绕同一任务发挥作用，这比把各自做成独立工具更容易形成使用价值。

文档专精作为这条主线的延伸：让实际代码改造同步产生可执行的迁移指南和排障说明。电脑系统操作继续使用 Hana 已有能力，暂缓另开系统操作专精路线。这个取舍来自现有模块的复用程度，尚未证明市场优势。

### 2.2 保留，并整合到任务中

| 保留的能力 | 产品中承担的职责 |
|---|---|
| 任务计划与进度、独立验收、中断恢复 | 同一任务的目标、状态、结果与接续，不各自再建一套流程 |
| 必要权限、脱敏和版本保护 | 工程执行底线，贯穿写入、恢复、协作及交接 |
| 按需代码审查 | 大改或有疑问时使用，结果绑定当前 diff 和证据 |
| 项目资料、技能与配方、服务和后台任务 | 按当前任务需要展开，低频动作放到详情或菜单 |
| 轻量记忆、新背景会话、通用交接包 | 减少重复说明和重复调查，保留来源与适用范围 |
| Pi 会话、模型循环、压缩与 Hana 界面框架 | 继续复用；增量以工程模块、Pi 插件和宿主适配提供 |

本轮对话没有提出需要再次更换宿主的已验证缺口，DSH 保留为将来的适配候选。下一阶段继续完善任务地图、版本化结果、计划与实际状态分离、内容导航及环境管理；实现以本仓模块和公开依赖为准。[既有宿主与功能取舍](../packages/enigma-engineering/docs/next-phase-plan.md)

## 3. 下一阶段最先做的三件事

### 3.1 把现有能力串成多仓任务流程

用户提出“升级服务接口并同步 SDK/应用”后，工作台应该围绕这一任务展示：相关仓库与源码依据、需要确认的契约、改造步骤、当前修改、联合检查及待验项。已有任务地图、计划、证据、产物和恢复模块提供基础；主要增量是连接与呈现。

第一轮用一个真实三仓迁移贯穿：从阅读到修改、验证、恢复和交接，找出必须反复手填或寻找数据的地方。先改善这些具体断点，再考虑增加其他入口。验收要能从任务界面直接看懂“改了哪里、为什么这样改、哪些检查仍未完成”，并展开到真实源码和回执。

### 3.2 先提供运行中手动切模

在任务运行时允许选新模型，显示“当前请求用 A，下一请求用 B”。无需停止任务或重发目标；当前工具继续完成，下一次模型请求接收实际结果。已经开始的回答仍由原模型生成，立即换掉它需要明确取消。

Pi 1.4.0 已提供每次请求前选择模型的 virtual model 扩展，路由状态能保存到会话分支；当前产品缺的是待切换状态、菜单交互和宿主显示同步。先解决手动切换，再做自动策略，用户更容易判断切换是否有帮助。[Pi 官方接口](https://github.com/earendil-works/pi/blob/v1.4.0/packages/coding-agent/docs/virtual-models.md)

### 3.3 让恢复保留失败经验和下一步

现有时光机负责恢复代码与上下文。下一步在恢复时留下简短记录：哪项假设失败、依据是什么、在什么条件下失败、什么时候可以重试，以及从此节点继续要做什么。复用现有记忆的来源、适用条件和版本，不新建平行记忆系统。

例如：“这个版本不存在接口 X，当前路线不能继续”，可以跨回溯保留；“一次网络超时”则不能成为永久禁止条件。验收用两个案例：同一失败不再重复尝试；条件变化后旧路线能够重新使用。较新用户要求、删除记忆和累计消耗继续遵守现有保护。

## 4. 模型分工如何建立在现状上

### 4.1 把两个新点子放在同一项能力中

模型分工决定**什么时候用哪个模型**；运行中切模负责**在下一次请求落实选择**。二者共用可选模型策略插件和 Hana 的配置/显示适配，继续使用一个主执行循环。

拟在新对话设置中提供“执行模型”和可选“规划模型”，各自可设置思考力度。按需复核沿用当前审查入口，将来允许指定模型。用户提出的 Kimi 规划、DeepSeek Flash 执行可作为拟议配置之一；默认选型以真实任务对照决定。

### 4.2 推荐的分工比固定 Plan/Code 更灵活

| 工作情形 | 推荐策略 | 理由 |
|---|---|---|
| 小改动、明确局部修复 | 单模型执行 | 减少额外规划与交接 |
| 多仓改造、接口和入口尚不确定 | 较强模型先阅读、规划并验证关键难点，随后交给执行模型 | 交接时已有可信的路线和代码依据 |
| 执行中出现新的方案问题 | 回到规划或临时升级模型 | 执行模型可以修订计划，而非机械照做 |
| 局部确定错误 | 保持执行模型，按真实检查修复 | 避免每次错误都启动重新规划 |
| 大改完成或结论有争议 | 按需独立复核 | 补充遗漏，最终结果仍由原验收证明 |

规划产物复用已有目标、仓库、步骤依赖和原检查，补上关键假设与重新规划的触发条件。真正的规划只读模式需限制工具和目录；当前“计划面板”只是步骤管理，不能自动等同于独立规划模型或只读权限。

先在相同任务与原检查下比较单模型、固定规划/执行、困难时升级三种策略，计入所有规划和失败返工。当前真实主链路使用 Gateway，尚无 Kimi/DeepSeek 配对实验；先比较响应等待、完成质量和返工，取得可靠计费信息后再核算费用。RouteLLM 与 FrugalGPT 提供路由/级联先例，问答研究不能直接证明本项目的编码收益。[RouteLLM](https://arxiv.org/abs/2406.18665)、[FrugalGPT](https://arxiv.org/abs/2305.05176)

### 4.3 切换需要守住的四个条件

- 当前模型回答及已派发工具先结算，不能重复执行写入。
- 新模型能接受当前上下文、图像和工具历史；容量不足先解释并处理压缩。切换可能损失提示缓存，避免每轮来回切。
- 只使用已配置且允许用于任务的模型，权限和验收标准不随模型改变。
- 界面区分策略选择、当前实际模型与待切换模型，记录各模型消耗；压缩、旁路问答及审查使用各自明确配置。

Pi 已记录虚拟选择和实际回答模型，适合在公开接口上扩展；跨 provider 的真实双向兼容、失败恢复和宿主同步仍需验收。[Pi virtual models](https://github.com/earendil-works/pi/blob/v1.4.0/packages/coding-agent/docs/virtual-models.md)

## 5. 其余点子合并成四条后续路线

### 5.1 代码理解、记忆与做梦：少重复调查

**已有：**源码阅读、任务地图、材料版本、范围记忆、中文检索、困难时推荐相关经验，以及不调用模型的草稿整理。

**增量：**把跨仓契约、相关调用方和联合检查记成带版本的关系；后续任务按问题召回，源码变化使相关结论重新待验。任务中的临时猜测先留在任务范围，确认可复用后才形成项目经验。

“做梦”是额外的模型后台整理：挑出近期有新证据且可能复用的少量草稿，去重、提炼、核对冲突，主任务恢复时让路。它应单独预算、可取消、保留新纠正；现有草稿整理不能被称为已经实现模型做梦。

先试跨任务契约复用，再试后台提炼。本项目此前小样本没有显示轻量记忆更快；衡量应包含任务结果、陈旧知识采纳、整理与检索总成本。Sleep-time Compute 和 ACE 可作机制参考，不能当作收益承诺。[本项目对照](../packages/enigma-engineering/docs/memory-comparison.md)、[Sleep-time Compute](https://arxiv.org/abs/2504.13171)、[ACE](https://arxiv.org/abs/2510.04618)

### 5.2 时光机、实验与交接：少走错路，容易接着做

将此前分散点子归到一项流程中：

| 时点 | 增量动作 | 复用基础 |
|---|---|---|
| 大改之前 | 用最小真实实验验证最影响方案的假设 | 阅读、契约、隔离方案和共同检查 |
| 放弃路线时 | 保留带条件的失败经验 | 时光机与项目记忆 |
| 压缩、恢复或交接时 | 对账原要求、当前版本、未知效果与未验项 | 已有要求保护、计划、背景包和状态旁路 |
| 接续任务时 | 给出最近有效证据和最小下一步 | 观察、计划和原始记录 |
| 完成交付时 | 简短列出目标对应证据与尚缺验证 | 当前验收与版本产物 |

“差量交接”在已有包上增加共同背景引用和变更摘要，接收端按问题补读。模型策略也可以随方案记录，在同起点、同原检查下比较。按依赖只恢复部分源码涉及更多一致性问题，安排在基础恢复验证后。

Kimi 官方 PR #2055 说明只回退聊天会造成 Plan/Todo/通知状态漂移，并将 undo 改为领域统一协调。该证据解释了恢复边界，不能证明某个最新版 UI 消失就是永久取消。后续沿用已有代码/上下文分开恢复与最新要求保护。[Kimi 官方 PR](https://github.com/MoonshotAI/kimi-code/pull/2055)

### 5.3 运行旁路与托管：先解释慢，再有限自救

**已有旁路：**在主任务运行时读取状态，解释阶段、输出活动、进程身份和最近证据。它不自动干预。

**先补观测：**显示在等模型、工具、审批还是子任务；期待什么终态、从哪里取得；最近有哪些源码或检查进展。静默和 token 增长都不足以判断是否有效。耗时优化先处理测得的重复读取、索引、快照和检查，模型切换只能影响模型阶段。

**再试托管：**独立监护进程读取现有事实，异常时按需问诊断模型。先只提出建议，再允许预授权范围内的重连、取消和有限重建。主进程挂死时，同进程旁路也可能停止；独立进程负责监护，模型负责解释。

压缩失败先判断请求、会话投影或展示哪层出错，恢复相应层。长验证先补可靠终态渠道与局部反馈。方案有证据表明错误时再准备时光机恢复；修复采集/通知适配器可以在隔离工作区试，任意 live 内核热改后置。恢复后必须核对原目标、旧执行是否停止及新副作用。Wink 提供异步纠偏先例，其研究范围不等于主进程全故障自救。[Wink](https://arxiv.org/abs/2602.17037)

### 5.4 文档专精：让跨仓改造能被别人照着完成

已有阅读、资料、验证与产物可以支撑第一项专精：**生成并维护跨仓 API/SDK 迁移指南**。每个字段、命令和步骤引用当前源码/Schema 或实际执行结果，改造完成后把文档与对应代码版本一起保存。

第一轮补三项：声明关联来源、示例实际执行、代码变化后提醒受影响段落重验。之后扩展技术设计、ADR、排障手册和跨文档一致性。源码能证明行为，设计动机要来自用户决策或设计记录。

验收使用真实三仓迁移：由独立流程照文档完成升级，保留原工程检查，注入过期字段和失效命令观察能否发现。文档结构与示例检查可复用成熟方法，不另建通用写作平台。[Diátaxis](https://diataxis.fr/)、[doctest](https://docs.python.org/3/library/doctest.html)

## 6. 推荐推进顺序与下一轮范围

| 阶段 | 做什么 | 进入下一阶段的依据 |
|---|---|---|
| 近期：把开发版用顺 | 完善任务流程、阅读结果呈现、进度/验收关联；收尾独立品牌、安装与更新配置 | 可以安装并独立完成一项真实多仓任务，少量常用入口覆盖主流程 |
| 下一轮增量 | 运行中手动切模、带条件的失败记录、恢复摘要；做一组规划/执行模型对照 | 切模无需重发目标、不重复操作；恢复少重复失败，原检查保持 |
| 工程专精 | 关键假设小实验、跨仓契约记忆、可执行迁移文档 | 真实联动任务与文档可独立复现，源码变更能使相关结论待验 |
| 可靠托管 | 等待关系与终态渠道、监护影子建议，再做有界恢复 | 能解释正常长任务；恢复不重复副作用，最终原目标仍通过 |
| 后续探索 | 按价值做梦、差量交接、按依赖局部恢复 | 连续任务实际复用，整理总成本与错误信息影响可核对 |

**建议下一轮先限定为：一条顺手的多仓任务主流程、运行中手动切模、失败条件与恢复摘要。**自动模型分工先试验；托管、做梦和文档专精保留后续入口，不同轮次的交付与研究状态要分别记录。

暂缓：每轮全量反思、固定多角色流水线、无限后台整理、凭超时全代码回滚、任意内核热修、通用全系统知识图谱，以及又一次整体换宿主。这些不影响现有计划、验收、权限、审查、资料和后台能力继续使用。

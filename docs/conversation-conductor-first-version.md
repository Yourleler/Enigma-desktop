# 任务编排管家：第一版与实践

2026-10-26。本轮依据用户追加要求实现。管家是一个独立的原生对话，接收目标和限制，再组织项目、工作对话与模型。它继续使用 Hana/Pi，会话控制与工程能力由 Enigma 插件组合。

## 第一版的使用方式

在工程项目侧栏点击“新建管家任务”，选择并发数、工作对话上限、可写仓库、可用模型和是否允许恢复。进入管家对话后描述目标；用户不必手工指定固定的角色流水线。

管家可以创建自己的项目、安排独立 worktree 中的工作对话、设置前置依赖、调整项目归属、选择模型和规划/执行策略，接收完成通知并查看旁路观测。它的限制由用户设置；模型可以进一步收紧，不能自行扩大。创建阶段顺序化，工作阶段并发，避免抢宿主创建状态或共享代码写入。

## 真实实践

实际 Gateway 在三个真实 Git 仓库中完成了一组任务：创建“只读双视角核查”项目，启动两个独立只读工作对话，一个检查函数调用链，另一个检查验收覆盖。两者的真实运行时间重叠，项目归属有效，原源码保留。

两份报告互相补充：源码视角找到上游→SDK→应用的函数消费关系；验收视角发现示例脚本只读取上游的一个文本文件，输出的“三仓通过”标记不能证明函数链已运行。管家据此应补充真实消费链检查，再做整体判断。这里是示例任务的验收范围发现，不代表已对所有产品任务证明效果。

已执行的角色分离、并发及权限流程见首轮实际记录（本地验收记录：`2026-10-26/enigma-desktop-completion/conductor-practice-r4/report.json`）。运行中切模还完成了同一任务内的两模型受控协议验证，见切模记录（本地验收记录：`2026-10-26/enigma-desktop-completion/model-switch-r1/report.json`）；Kimi/DeepSeek 配对效果尚无实测。

第二项真实 Gateway 实践验证了“代码升级＋迁移文档＋消费链验收”：两项工作在独立工作区实际并发，一项修改 alpha 的返回值，一项在 beta 编写迁移指南；选择成果前原仓库保持不变。管家分别预览和整合，两次都运行并保留原 joint 与 consumer-chain 定义，最后核对当前有效验收证据，并保存报告到原生对话文件。

原 joint 仍只检查文本值；新增 consumer-chain 实际调用 gamma→beta→alpha 并断言 `gamma:beta:alpha-v2`，从而解决第一项实践暴露的覆盖缺口。记录见代码与文档协同实践（本地验收记录：`2026-10-26/enigma-desktop-completion/conductor-integration-r4/report.json`）。这验证了并发产出、选中整合、真实消费链和报告登记；尚未验证第三个陌生对话完整照文档操作、跨文档持续维护或所有恢复场景。

## 怎样从能力组合出额外价值

管家接收的是目标、允许范围与验收标准，不预设“几个角色做完就算成功”的固定流程。角色、先后关系、是否并行、是否需要额外复核，都根据实际证据决定。优先增加可复用的控制动作，再用实践筛选组合方式；不为每个灵感堆一套专用开关。

现有能力有三组：读取代码、材料与记忆来形成依据；用模型分工、隔离任务、计划与时光机探索路线；用旁路、验证证据、变更阅读与交接包核对成果。它们组合后，以下用途比单纯“把任务分给多个 Agent”更值得做。

| 用法 | 管家组织的动作 | 现有依据与下一步 |
|---|---|---|
| 核对“完成”是否可信 | 分别安排源码、执行证据或文档视角，汇总覆盖缺口 | 双视角实际实践已有结果，下一步加入真实消费链验证 |
| 比较不同方案和模型 | 相同起点创建独立任务，使用共同检查比较后选择 | 隔离、模型选择及现有方案实验可复用，整体编排比较待实践 |
| 多仓库迁移 | 根据契约安排生产方、消费者、集成和文档任务，处理前置关系 | 三仓基础与暂存智能阅读已通过，任务群成果集成继续补齐 |
| 代码与文档共同维护 | 变更阅读指出影响，再安排说明和可执行示例核对 | 版本来源与产物已有，文档专精仍在当前补全范围 |
| 接续长任务 | 汇总各对话有效证据，选择下一步，遇到变化重新安排 | 原要求、交接和恢复基础可复用，管家持久接续继续验证 |
| 异常排障与隔离维修 | 从旁路查等待对象，安排复现/诊断，再在隔离任务中修组件 | 独立监护进程基础已写，广义托管控制与故障集验证继续完成 |

| 进一步的组合 | 一个具体使用目标 | 做法与收益 | 当前边界 |
|---|---|---|---|
| 先反证，再投入 | “这个重构可能收益不大，先找能推翻它的证据” | 建立最小实验；一项任务提出路线，另一项专找失败条件，确定值得做后才展开大改 | 隔离、来源与原验证已有；需要实测不同方案的收益，不能把模型意见当实验结果 |
| 让陌生人照文档做 | “不用问作者，照迁移指南把消费者升级成功” | 写作者提供指南，新的对话只拿必要背景和指南，记录缺失步骤与实际命令结果；反向更新文档 | 代码/文档并发写入和整合已实现；完整照做与段落维护仍需验收 |
| 多仓契约雷达 | “上游这个接口变化，哪些项目、说明和测试会过期” | 从变更阅读追踪消费链，再分配消费者、契约检查、文档同步；保留统一版本与原验收 | 来源阅读和多仓范围已有；跨任务持续扫描与记忆关系维护仍需补全 |
| 失败路线的止损与复用 | “不要让每个工作对话重复踩同一个坑” | 先确认失败条件和版本，再把经验作为有条件的背景交给后续任务；时间回退保留原要求和外部效果 | 时光机、轻量记忆、接续已有；自动整理、去冲突与删除继承仍待整体实现 |
| 任务中途改组 | “新证据说明这条路线不对，把剩下的工作重新安排” | 保留已有成果，取消已失去价值的工作，调整模型和依赖；接续同一隔离工作区而非重复创建和重跑 | 已实现取消/接续/权限撤销；动态重组收益仍待真实场景证明 |
| 对照验收方法 | “测试一直绿，可用户遇到的问题还在” | 一项任务检查源码行为，一项检查测试到底证明了什么；对照原要求和实际消费链，补上缺失验证 | 只读双视角实践已经揭示真实覆盖缺口；补充检查不能删除或弱化原检查 |
| 最小背景交接 | “把这个支线给别的 Agent，又不带上所有历史和失败尝试” | 用来源、版本、当前权限、尚未完成的要求与最小下一步形成交接包；接收方重新核对实际文件 | 基础交接包与适配已有；管家直接编排异构宿主尚未完成 |
| 花费与延迟分配 | “小问题别用最贵模型，复杂决策别让廉价模型反复试” | 查看错误、请求量和有效证据，按允许的模型分工和预算重排；保持真实使用量，策略修改不清零 | 运行切模、角色力度、请求预算已有；没有真实价格/时长评测前不声称省了多少 |
| 研发过程回放 | “为什么选这个方案，后来什么变化使它不再适用” | 连接原要求、关键假设、实验、被否定的路线、选中改动与验收证据，输出可回查的决策报告 | 来源、时光机、成果报告已有；完整证据图与长期记忆关系仍待补齐 |

这些不是都已完成的功能清单。第一版优先实际验证“互补视角”和“代码与迁移文档协同”，其余根据底层控制和具体证据逐项推进。目标是减少重复背景、无效尝试和不可信收尾，并让长任务能被理解和接管。

这些组合是可以探索的用法，不能把每一项都称为已经实测完成。管家工具接收通用目标和范围，不把用户举例固化成唯一工作模式。

## 当前进入下一轮的工作

第一版已验证原生项目、两个真实只读工作对话、实际并发和源码保护。后续补入 `preview / integrate / verify / report`：固定来源预览、选中成果整合、原联合检查和可下载报告；专项覆盖并发用户修改保留、冲突/过期拦截和证据失效。收紧权限会停止受影响的已运行工作对话并撤销原授权；冷加载把无终态的旧任务标成待接管，不自动重复执行。`resume` 保留原工作区和历史，在核对未决效果后接续。

`diagnose / supervise` 可组合独立旁路问询及监护进程，覆盖任意当前任务/等待/故障问题。独立进程与受控动作专项已通过；界面有独立观察与诊断入口。诊断解释是建议，自动动作仍核对授权、观察版本、旧执行终态与预算；不会因耗时长直接回滚或替用户审批。实际原生任务联调和故障覆盖继续完成。

管家不能仅凭工作对话自报成功替用户结束整个目标；原检查通过也只证明其覆盖范围。整体完成仍须对账其他原要求。

当前整体 Goal 仍包含功能补全、记忆、文档、广义托管、完整界面与构建验收，见[执行清单](full-capability-completion.md)。本页记录第一版实践，不替代整体完成报告。

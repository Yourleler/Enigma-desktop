# 当前能力与后续组合计划

更新：2026-10-30。本报告以[本轮重验](goal-revalidation-2026-10-30.md)和 README 第 3 节的最终使用目标为基础。下面的新增组合属于方案，不因写入报告而自动实施。

## 产品方向

以日常 coding agent 为基础，专精“跨仓库修改及其文档维护”。重点不是增加更多面板，而是让一次接口升级能贯穿公共库、服务、SDK、应用、测试和说明，最后交付可以直接验证的结果。

目前已有多仓领域模块、问题驱动阅读、方案纠偏和文件恢复、原要求验收、记忆与增量整理、旁路与托管、任务编排、模型分工、背景交接和文档校核。UI、权限与各功能边界仍需结合真实任务持续打磨；不能把有入口视为所有使用场景都可靠。

## 现有能力如何组合使用

| 场景 | 用户交代什么 | 现有组合 | 应交付什么 |
|---|---|---|---|
| 接口升级 | 目标版本、相关仓库、兼容限制 | 任务阅读→契约/计划→多仓修改→原消费者验收→文档校核 | 可运行变更、原检查结果、迁移说明与未覆盖项 |
| 不确定技术路线 | 目标、候选方案、时间和费用上限 | 假设检查→隔离尝试→对照证据→时光机保留教训 | 哪条路有效、为何放弃其他路径、保留的改动 |
| 长任务离开电脑 | 目标、可用模型与可执行动作 | 旁路解释→有界托管→必要时恢复或请求帮助 | 实际进展、等待对象、干预原因和可继续的状态 |
| 相同背景做另一件事 | 要沿用哪些项目背景、是否继续原目标 | 项目共享资料→新对话/Fork→交接包 | 不必重复描述，且不会误继承旧 Goal 或扩大权限 |
| 多视角处理同一项目 | 最终目标、可并行部分和写入限制 | 管家创建工人→隔离工作→冲突预览→选择整合→群体验收 | 统一结果与证据，明确每个工人的贡献和未决项 |

模型选择可以先用单模型。需要时再按“决策、执行、独立复核”分工：按能力和验证结果分，不强迫所有任务都跑三套模型。运行中改选模型在下一请求生效，正在返回的内容不应被突然切断。

## 建议增加的点子

| 优先级 | 点子和要解决的问题 | 建议设计 | 成本与成效判断 |
|---|---|---|---|
| P1 | **失败经验在行动前提醒**：模型经常重走刚失败的路 | 用时光机教训和来源条件，在相同前提再次出现时给短提醒；允许确认前提已变而重新尝试 | 中；看重复无效操作次数，不能用“召回了几条”衡量 |
| P1 | **验证方法替换**：检查本身过慢，任务长期没有结论 | 先保留原验收要求，按证据选择等价的更小检查；只能标为暂时替代，最终交付仍需满足原条件 | 中；比较等待时间和漏检率；不能仅因慢就回溯或宣称通过 |
| P1 | **变更说明自动跟上代码**：代码对了，文档与示例过期 | 从固定版本变更集生成受影响段落清单，再用真实示例核对；每段给来源和验证状态 | 中；过期段落命中率、示例真实执行结果、人工改写量 |
| P1 | **成本与收益对照**：换模型、复核、回溯是否值得不清楚 | 在既有模型用量基础上记录角色、干预与结果；模型、角色、任务是不同维度，不能直接相互代替 | 中；相同任务的总成本/耗时/成功率；缓存、重试与估算单独注明 |
| P2 | **阻塞原因图**：看得见运行，却不知道谁在等谁 | 从实际事件关联模型、工具、审批、服务与子任务；没有证据时显示未知；点击能看最后事件与下一步 | 中；定位时间、误报率与诊断开销 |
| P2 | **项目交接按需补读**：完整复制上下文太贵，摘要又可能遗漏 | 交接包带背景、原要求和可取回的来源索引；新 Agent 通过公开接口按需取证，重新确认权限 | 中高；遗漏率、传输量、失效来源比例 |
| P2 | **记忆保鲜与低成本整理**：大量历史不能全塞进上下文 | 先按来源版本、作用域和使用反馈筛选，再由合适模型合并候选；暂停、预算、删除与纠正保持生效 | 中；有用召回率、错误经验率、整理成本；需要长期样本 |
| P3 | **托管器修复自身周边组件**：渲染/压缩/观测失败让任务无人照管 | 独立监督进程记录检查点；诊断后只在隔离副本试修，经过限定验证才请求或执行授权替换 | 高；主进程故障、重复执行与未知副作用是核心验收；不能授予无限自修改 |

## 时光机与管家的边界

时光机修正的是上下文路线；代码恢复是另一种操作。两者都不能撤销已经发出的外部请求。管家应优先诊断、缩小检查或切换执行手段，只有证据表明路线失效才回溯。回溯必须保留最新要求、经验、当前文件、原始记录和累计费用。

“持续运行很久”不等于“有意义地工作”。诊断要展示最后有效进展、当前等待对象和信息缺口。仅凭超时自动否定一个验证方法容易产生假完成，因此托管需要操作级预算、幂等记录和明确的未知结果。

## 暂时不增加

- 固定多角色流水线、重复规划和每轮反思：增加费用及等待，先由任务需要触发。
- 通用企业记忆平台：先把个人项目的有效来源、纠正和删除做好。
- 无约束的管家自修、自行发布和自动对外沟通：现有授权模型不支持这种承诺。
- 把 UI 动效或“正在分析”当进展证据：动效只负责可感知状态，内容必须来自真实事件。

## 推荐顺序

先完成当前 Goal 的正式安装和边界复验。下一阶段优先验证“失败经验提醒、验证方法替换、代码与文档一起维护”三个小闭环，每个用真实任务比较前后效果，再决定是否加入默认流程。成本对照和阻塞解释随后接入，长期记忆与自修管家按独立实验推进。

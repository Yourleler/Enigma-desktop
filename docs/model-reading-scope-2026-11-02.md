# 模型解读的实际材料范围

## 问题

原实现先取前100个源码节点、前120条关系、前30个文件，再把序列化JSON直接截为100000字符。这可能截断JSON结构，也没有记录模型实际得到的材料。返回的节点引用只检查是否存在于整份报告，没有限制在本次实际输入中。

## 修正

- 按模型上下文和材料字符预算生成完整JSON批次，不再按节点/文件固定取前若干项。每个已记录节点与文件摘要都进入批次；单份过大或超过12批时显式失败，并保留已完成的源码分析，不静默省略。
- 单次任务保持既有超时、权限和模型请求限额；每批发起前再次核对。每批最多两组章节与两条说明，以满足原有报告总量限制。
- 连线只随本批实际提供的两个端点发送，记录提供/总量。跨批次或超出预算的关系不冒称已解读；源码片段和差异摘要有裁剪时标记。
- 返回说明必须引用本批实际提供的节点，正文、数量与结构通过校验后才保留。后续批次失败、取消或超出限额时，失败状态保留，同时提供源码分析与前面有效的说明，不能冒称全部成功。
- 保存请求批数、有效返回批数、节点/变更/关系范围与裁剪计数。UI说明这是请求材料范围，不代表模型逐字理解、全量审查或计费Token。
- 每批使用独立的既有用量记录，保留该请求的缓存、耗时和供应商数据，不把多次请求合成一个耗时。Pi的`reasoning`按输出Token子集读取，已报告0保留为0，缺失或null保留未知，不重复加到总量。

报告新增`modelCoverage`是schema 1的可选信息；失败任务允许保存已校验的部分结果，任务终态仍为失败/取消。存储契约、兼容性审查、指纹及运行依赖清单已同步。数据纪元仍为1，不重写旧会话、旧文件或旧报告。

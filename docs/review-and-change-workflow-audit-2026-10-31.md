# 对话变更、智能阅读与审查：现状和补齐要求

日期：2026-10-31。核查基线：`45d1562f`，应用版本 `0.452.161`。

本文件保留初次核查基线；后续实现及验证见[0.452.169 对话变更与审查工作台](conversation-review-workbench-2026-10-31.md)。以下“缺失/待办”描述的是初次核查时的状态。本文件只记录本项目的需求、实现与验收要求。

## 结论

审查不应以 GitHub 为前提。Enigma 已能读取本地 Git 变更，但普通对话的变更入口仍依赖 Git；独立审查仍需要先选择工程代码快照。它们尚未组成“在对话中直接查看本轮改了什么，然后审查这些修改”的完整流程。

这里要区分三个对象：

| 对象 | 用户想做什么 | 前提 |
| --- | --- | --- |
| 对话文件变更 | 看本轮、整个对话或两轮之间产生的代码和文档变化 | 保存明确的轮次及文件前后版本，不应要求 Git 或远程平台 |
| 仓库变更 | 看工作区、暂存区、分支、提交或 PR/MR 差异 | 本地 Git；只有远程请求相关功能需要相应平台 |
| 对话内容检查 | 核对回答是否遵循原要求、证据是否充分 | 选定消息和材料；这是另一种检查对象，不能把文件 diff 当成对话文本审查 |

第一类是本轮最重要的缺口。第三类可作为后续独立模式，不以含混的“对话审查”名称混入第一类。

## 逐项核查

| 能力 | 当前实现 | 判断与用户影响 |
| --- | --- | --- |
| 本地变更，不连接 GitHub | 普通侧栏发现会话目录的 Git 根；工程可登记多个仓库 | 已有。不能再向用户解释为必须有 GitHub |
| 普通目录的对话变更 | 非 Git 目录不能生成侧栏差异 | 缺失。普通文档任务无法按轮次审查产物 |
| 本轮、整个对话、任意两轮 | 普通侧栏仅工作区/暂存区；工程来源为工作区/暂存区/提交/MR | 缺失。工作区差异可能混有其他对话或用户原有修改 |
| Git 分支/提交范围 | 引擎有按仓库指定 base/target 的能力 | 部分具备。普通侧栏没有完整的分支、提交历史选择流程 |
| 同版本差异与阅读 | 两者共享冻结的变更记录，并提示当前代码是否变化 | 已有，应保留 |
| 智能解读 | 工程工具可调用模型生成带源码锚点的解释；普通侧栏构建未传入解释器 | 入口不一致。普通侧栏主要显示静态职责和源码关系，不能宣称处处都有完整 AI 解读 |
| 核心改动与辅助改动 | 有章节、源码节点、文件分类及影响关系数据 | 部分具备。没有完整的行为改动点→核心片段→辅助文件的阅读流程 |
| 全量 diff 阅读体验 | 单文件文本差异、增删色、截断提示与可用时的完整展开；超过 8 个文件才显示路径筛选 | 需要补齐双栏、片段跳转、常驻搜索、文件树/平铺及显示控制；长差异当前会退为纯文本 |
| 来源与高级筛选 | 目前主要按路径子串筛选 | 缺少产物/仓库、多仓库组合、扩展名、包含/排除路径等完整筛选 |
| 风险条目 | 模型解释里可包含风险；独立审查保存文本报告、状态和覆盖信息 | 缺少逐条严重度、来源锚点、处理状态、修复与复查记录。不能把一篇报告算作可操作的审查工作台 |
| 影响关系 | 有源码边、跨仓职责、依赖、需求与测试关联 | 已有基础；目前以列表/详情展示，缺少交互关系图和改动点联动 |
| 独立审查隔离 | 新 Pi 上下文只读冻结版本，独立模型、请求统计与覆盖记录 | 已有。审查意见和实际验收分开，不应削弱 |
| 来源过期判断 | 源码、环境、配置、证据变化会使报告过期或需重新核对 | 已有。统一界面时仍需展示 |
| 文件、浏览器与文档面板 | 已有可定制右侧标签、同框预览、分栏调宽、文件搜索和 Chromium 集成 | 无需重写底层。重点是与变更、审查及任务上下文互相跳转 |
| 子助手查看 | 任务卡中能展开子会话和状态 | 部分具备。独立标签、多子任务选择和返回父对话定位还需统一；本轮未做新的端到端验收 |

## 补齐后的交互

右侧保留一个“变更与审查”入口，内部按任务切换“智能阅读 / 文件差异 / 审查意见”。不要再让普通对话和工程工具各有一套不同能力。

顶部先选择来源，默认“本轮变更”；可选“整个对话”“选择轮次”“仓库变更”。只有选择仓库来源时，才展开暂存区、分支、提交等 Git 控件。没有 Git 时，对话代码、Markdown 和其他产物仍能进入。

阅读区先说明范围、改动目的与主要行为变化；每个改动点可以跳到相应冻结源码、完整差异和风险。原要求、模型推断、源码事实及实际检查结果分别标注。涉及代码执行结果时，没有证据就不能写成已验证。

“开始审查”直接采用当前选择的范围，并展示将使用的模型和范围完整性。风险列表逐条呈现严重度、原因、可能影响、源码锚点和处理状态。请求修复进入当前任务的正常调度与权限流程，修复后对新版本复查；“已修复”必须有复查依据，不能仅靠模型宣称。

多仓库共用同一对话范围，文件按目录身份分组。用户切换标签后，来源、文件、阅读位置、筛选条件和风险选择保留。窄窗优先收纳筛选项，不压缩到只剩图标或遮挡正文。

## 实施顺序与验收

优先级是本项目的补齐顺序，不代表所有现有功能不能使用。

### 1. 首先补齐：可靠的对话文件变更

保存不可变的“对话—轮次—文件版本”记录；至少包含目录身份、文件路径、操作归属、前后内容标识、新增/删除状态、完成/中断状态和缺失原因。对话分支及回溯保留原记录，不能把新旧路线混在一起。

现有文件历史可以复用存储和监听，但不能直接充当轮次账本：60 秒合并会覆盖中间版本。工具前备份也不能覆盖首次创建、全部命令副作用及并发修改。应结合明确的轮次边界、工具操作记录和结束核对；外部或归属不明的修改必须单独标注，不自动算到当前模型头上。

验收至少覆盖：

1. 无 Git 目录两轮修改同一份文档，能准确查看每轮和累计差异。
2. 原有未提交修改、用户并发编辑、另一对话的修改不会被错误认领。
3. 两个仓库与一个普通资料目录共同参与；目录权限独立生效。
4. 新建、删除、重命名、二进制、过大文件、命令写文件有准确状态；无法完整捕获时明确说明。
5. 中断、重启、分支、时光机跳转后仍能读取原版本，不覆盖当前文件。
6. 旧对话没有完整版本时显示“历史记录不完整”，不靠时间戳伪造精确轮次。

### 2. 然后补齐：统一阅读与差异

让普通侧栏复用完整解释路径，但模型调用按需发起，有运行、取消、失败与费用状态。按冻结版本缓存，版本变化时不能沿用旧结论而不提示。

把现有冻结来源和源码分析数据接入统一 diff 组件，增加单/双栏、核心片段/完整文件、上下处变化、搜索高亮、文件树、换行和筛选。可评估成熟开源组件；引入前核对许可证、现有技术栈和大文件行为，保留真实复用说明。

验收包括普通/工程入口得到一致范围、相同版本的解释与 diff、深浅主题高亮、键盘操作、长行/大文件、窄窗、切换标签恢复、过期与失败提示。缺少内容或被截断的文件不能称为完整阅读。

### 3. 同期补齐：结构化风险处理

定义稳定风险 ID、严重度、事实与影响、冻结源码锚点、待处理/待复查/已处理/已忽略状态，以及处理原因和复查证据。关联新旧版本时要核对来源，不能仅按标题认定相同风险。

验收包括：从风险跳到正确版本与行；选择部分风险修复；忽略原因可追溯；修复过程中来源变化；复查失败/取消/超时保留待处理状态；刷新、切换对话和重新审查后状态不会错绑。

保留独立只读审查及原验收标准。审查阶段不能自动编辑项目；修复是另一个明确的任务动作，不让审查模型同时给自己的修改盖章。

### 4. 最后增强：影响关系与相邻面板联动

在已有源码图数据上增加可缩放、可聚焦、可筛选的关系图，并从改动点和风险跳转。给静态确认关系与模型推断不同标识，不把图画出来当作运行验证。

将子助手、文档、原要求及实际检查证据接入同一右侧标签体系，复用已有预览和运行记录。补父子对话定位、需求到文件/检查跳转和阅读进度。不要为外观相似而重做浏览器或文件引擎。

# 空对话模型恢复与管家工作对话补验

稳定更新版本：0.452.258。系统通知实验独立保留在`codex/notification-navigation`，不包含在本次稳定更新中。

## 发现的问题

真实管家测试创建了一个只读工作对话，但工作对话在第一次模型请求前失败。会话记录显示：先选中了授权模型，工程工作区重载后又变成助手默认模型，随后被管家的模型范围检查阻止。任务卡只标记失败，没有保留实际错误。

Pi 1.4.0根据是否已有消息决定是否恢复历史模型。刚创建的工作对话已有`model_change`，却尚无用户消息；原宿主依赖SDK恢复模型，在此阶段会退回默认值。

现在宿主明确传入会话已记录且当前可用的模型。不可用模型仍保留原身份并阻止请求，不静默换模型。任务首次执行与接续共用终态处理：保留具体提供方错误，区分失败和取消。

## 项目与可读性

- 未指定单独项目的工作对话默认继承管家的项目归属；独立对话标记也保留。隔离代码目录不再被当作新项目自动散落到侧栏。
- 目录项目按项目本身的路径命名，避免被成员工作区的内部目录编号替换。旧隔离工作区优先显示工作区名称；没有挂载名称的旧工作对话用已有任务标题替代生成的目录编号。最后的打包Web复核已看到可读任务名。
- “独立管家”明确改称“旁路观察”，与安排多个工作对话的任务管家区分。
- 停止观察的提示改为“主任务状态未改变”，不把原本空闲的任务说成正在运行。
- 审批模型未产生有效结果的错误提供中文说明，保留未执行的事实，不绕过审批。

## 实际验证

修复前的测试和失败记录保留。首次用例也禁止程序内部Git操作，实际工作区准备涉及Git元数据读取，因此该用例不记为通过。随后明确将测试范围分为：允许程序准备隔离工作区所需的内部Git元数据操作；禁止模型调用命令工具、写文件、发送通知或外部消息及创建额外任务。

修复后的真实模型测试仅创建1个工作对话，记录中两次模型选择均为授权模型；仅调用`repo_read`，正确返回`compilerOptions.target`为`ES2022`。工作对话终态为completed，活跃任务数0，137个测试源码文件哈希全部未变。

Web任务卡显示1个工作对话、2次累计模型请求和源码依据，同时保留“验收仍需核对”。点击进入工作对话可看到读取结果，再点击返回可回到对应管家的原任务内容。没有把工作对话执行结束当作整个项目目标完成。

旁路使用实际配置的审批模型通过审批并启动独立进程；停止后确认原进程退出，干预次数0，界面保留“已停止观察”。此前本地通知夹具无法给出有效审批的失败单独保留。

项目菜单实测可以将对话移出项目，放入“最近对话”，并保持原工作目录及历史；项目与最近对话可分别折叠。

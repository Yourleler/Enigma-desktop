# Enigma-next 后续创新与文档专精计划

2026-10-25，Asia/Shanghai。本文在既定功能的 macOS 完整回归、真实三仓库流程和交互界面复验后撰写。内容为后续方案，不启用新插件、自动托管、模型做梦、自动回溯或内核维修。现有代码能力、公开来源事实和设计判断分别说明。

## 1. 建议方向

建议继续以个人多仓库 coding agent 为基础，下一项专精优先探索“跨仓库迁移与可验证文档维护”。它服务接口升级、SDK/调用方联动、迁移说明、排障和技术设计，能够复用现有源码阅读、项目资料、原检查、分支实验与版本产物。文档能力应覆盖事实来源、可运行步骤和变更维护，而不仅是润色文字。

机制创新优先研究三个问题：开始时如何少押错关键假设，回溯后如何避免再走同一失败路线，长任务如何保住要求并取得真实终态。托管管家放在这些基础之上，先观察和有限恢复，再考虑隔离维修。电脑系统操作可以后续探索，但当前宿主 shell 并非 OS 沙箱，系统配置、账号与外部副作用的边界明显更大，复用现有能力的收益也没有文档/迁移方向直接。

这是产品取舍，不是已证明的市场胜负。公开产品和研究已经分别提供检查点、异步纠偏、经验更新与空闲计算；没有足够证据断言这些点子无人做过。Enigma-next 的机会在于把个人工程任务中走错、等待、失忆、取证和交付的问题连接起来，且每一步都能被实际结果否定。[Wink](https://arxiv.org/html/2602.17037v2/)、[ACE](https://arxiv.org/html/2510.04618v2)、[Sleep-time Compute](https://arxiv.org/abs/2504.13171)

| Diátaxis | 按教程、操作指南、参考和解释区分读者需求 | 它是文档组织方法，不是代码事实验证或写作模型。[官方方法](https://diataxis.fr/) |

## 4. 减少走弯路的机制候选

下表均为设计提案，低/中/高表示相对实现成本，优先级来自当前个人多仓库方向的取舍，没有编造收益数字。

| 机制与场景 | 建议动作与现有复用 | 相邻方案与增量 | 成本 / 风险 | 怎样验证 / 优先级 |
|---|---|---|---|---|
| **先证伪关键假设**：接口或入口猜错，改完才发现 | 找最影响方案的少量前提，用真实请求、构建或调用验证；关联来源版本和受影响步骤。复用阅读、契约与实验 | 与反馈试验相邻，增量是开始前寻找能否定方案的实验，而非事后总结 | 中；小实验可能绕过真正集成难点 | 比较返工、漏项和前置开销；高 |
| **回溯留下失败条件**：回退后再试同一条错误路线 | 保存“版本/配置/错误/失败判据”，代码回退而事实保留；条件变化后重新开放。复用记忆与树节点 | 借鉴增量经验，增量是跨回溯保留适用条件与解除条件 | 中；短暂断网被误记成永久禁令 | 包含旧方法后来正确的反例，统计重复失败和错拦；高 |
| **两条路线先做难点小试验**：大改后才知方案不合适 | 在独立方案中测试成本最高的风险，使用同一成功标准，再投入完整实现 | 现有实验已可比较完整方案，未来增加成本上限和最先失败的共同难点 | 中；实验省略真实用户路径 | 以完整联合验收衡量最终收益，计入实验浪费；高 |
| **压缩/交接前后对账**：长会话忘掉不能改和必须验 | 将要求来源、当前版本、验收缺口和未结算效果单独对账，缺项回读原记录 | 复用原始要求门禁和交接，增加压缩后可核对的差异 | 中；摘要反向改写原要求 | 人为遗漏约束后必须发现，区分用户更新与摘要丢失；高 |
| **等待前准备终态渠道**：任务发起后无法查结果 | 明确本次运行标识、谁产生结果、查询/回执和备用取证；缺渠道先补观测 | 现有等待处理已知来源，未来在开始前识别无法结束的等待 | 低至中；通知被误当成成功 | 注入丢事件、过期认证、错误 run ID；高 |
| **保留原标准的分层验证**：整套验证太贵 | 先跑最能揭露错误的局部检查，再保留原完整检查与未结算项 | 不是把小测试替代集成测试，而是改善反馈次序 | 中；偷偷缩小验收范围 | 原检查清单不变，比较总耗时和最终漏项；高 |
| **按事实到期复验**：昨天环境可用，今天已变 | 给外部接口、工具与材料设置核实条件；变化只影响依赖它们的结论 | 现有 hash 保鲜主要覆盖本地，未来覆盖外部可变前提 | 中；暂时失败被当成事实改变 | 版本变化与临时失联分别注入；中 |
| **差量交接**：新会话重述全部背景 | 共同背景只传引用，新任务单独表达；目标端对账后补读取变化部分 | 复用现有包，增加接收端问题驱动的补充，而非无损迁移隐藏状态 | 中；变更摘要漏掉关键文件 | 比较重述时间、陈旧事实采纳与遗漏要求；中 |
| **中断后的最小下一步**：隔几天回来不知怎么继续 | 展示最后有效目标、未解假设、证据和可执行下一步，先核对当前环境 | 复用观察、计划和交接，增加任务恢复的使用体验 | 低；把旧摘要当现状 | 工作区/权限变化后能指出缺口，恢复时间有记录；中 |
| **只整理值得复用的知识**：做梦成本高且用不上 | 根据真实复用和变更选择少量材料，主任务恢复后让路，记录成本与实际使用 | 借鉴 sleep-time 与 ACE，避免频繁全量总结 | 中至高；抢占 Gateway、污染记忆 | 计算整理和检索总成本，不只看前台延迟；中 |
| **最小范围恢复**：一个验证器故障却回滚整项成果 | 分别恢复展示、请求、工具尝试、上下文或代码；只退有证据失效的层 | 复用检查点，未来需记录读写依赖，不能凭工具名猜撤销范围 | 高；漏依赖导致跨仓不一致 | 与完整恢复比较数据保护、正确率和重复操作；后置 |
| **交付时给完成凭据**：新 Agent 把旧声明当通过 | 输出要求→当前证据→版本→未知项的简短记录，源码变化后失效 | 复用地图、检查与产物；未来跨压缩/交接/干预始终可追查 | 低至中；凭据成为另一份过期摘要 | 独立回查每项来源，旧版本不得认证新成果；高 |

“关键假设先取证＋失败条件留下＋完成凭据”最适合作为第一组试验：它们改变任务顺序和事实保存，单独也有使用价值。它们不要求固定角色、每轮反思或另一名常驻模型。

## 5. 托管管家的后续路线

管家负责解释停滞、控制有界恢复和核对恢复结果，主 Agent 负责工程任务。主进程的事件循环若阻塞，同进程提示词或定时器也可能停止，因此真正救援应采用独立进程：确定性规则监控本地状态，模型在异常时提供诊断建议，公开 Pi 适配器执行已授权的控制。详细分析见 [托管可行性](supervised-mode-feasibility.md)。

| 层级 | 优先能力 | 停止条件与保护 |
|---|---|---|
| 只观察 | 回答当前阶段、等谁、证据是否更新、采集是否失效；先用影子建议测误报 | 不凭静默或 CPU 判死，不占主工作区锁 |
| 有界恢复 | 取消超限请求、重连页面、确认旧执行停止后有限重启/重试 | 取消应答不等于物理终止；未知效果不重放，独立预算与运行代次约束 |
| 方案恢复 | 证实路线错误后准备恢复预览，保留原要求、用户改动、失败条件与未验项 | 原检查不能被管家删除或放宽，外部副作用不能假装回退 |
| 隔离维修 | 在新工作区修可替换的采集/通知/压缩适配器，故障案例与回归后切换 | 不热改内存中的任意内核，不自行扩大权限或修改成功标准 |

压缩卡住通常先处理请求和会话投影，未必需要回滚源码。摘要已提交但页面没刷新时只修展示；请求未完成则取消并等终态；主进程无响应时确认拥有的执行停止后，从最后有效会话重建，原用户记录仍是要求来源。无法取到后台结果时，可以补本地查询/通知适配器，但必须重新取得本次终态；“通知成功”不填补验收缺口。

本次实际修复也说明这些区别：立即取消可能在初始化后仍派发；页面可能漏掉最终刷新；Windows 状态发布遇到原子替换失败也会留下旧“运行中”记录。恢复需要分别验证执行、状态发布和展示，不能全部叫成“卡住”。

试验应覆盖健康静默长任务、限流、压缩已提交/未提交、PID 重用、观察器死亡、两个管家竞争、用户接管、旧后台事件和错误维修补丁。统计误杀正常任务、最终原验收、重复副作用、人工介入与总成本，不能只报自动重启次数。共享 Gateway 拥塞时，管家至少应能靠本地事实解释与停派发，不能依赖第二个模型请求一定更快。

## 6. 文档编写作为专精能力

### 6.1 面向真实使用场景

| 文档任务 | 读者真正要完成的事 | 拟议能力与验收 |
|---|---|---|
| API/SDK 迁移指南 | 确认生产者、SDK 和调用方的改法，完成升级 | 关联 Schema、源码与版本；旧/新示例分别执行，迁移步骤在新环境复现 |
| 技术设计与 ADR | 理解方案为什么这样选、哪些限制还在 | 关联源码和实验，用户决策与事实/推断分开；不能从代码编造设计动机 |
| 排障与运行手册 | 定位错误，执行恢复并确认终态 | 真实错误/日志来源、环境适用条件、可执行诊断和停止条件 |
| README/操作指南 | 从安装到运行完成一条用户流程 | 先确定读者与前置条件，隔离环境跑所有必要命令，失败保持可见 |
| 需求与验收文档 | 确认目标、范围、非目标和验证覆盖 | 原要求保留来源，验收只关联现行证据；不让写作改动偷偷放宽条件 |
| 研究与说明材料 | 区分证据和判断，理解方案取舍 | 来源及获取时间、引用核对、反证与不确定性；不扩写未经支持的结论 |

组织方式可借鉴 Diátaxis，但不强制所有项目套四份文件。参考内容、操作步骤和背景解释服务不同读者；一个短 README 可以分清用途，不需要变成繁杂的模板体系。[Diátaxis](https://diataxis.fr/)

### 6.2 关键增量

**文档声明关联来源。** 对接口字段、默认值、权限、支持版本、性能结论和恢复承诺建立可核对的来源。声明分别标为已运行、静态支持、用户决定、模型推断或待验证。来源位置/hash 和适用版本变化时，仅重新查受影响声明，不自动重写整份文档。源码能证明行为，不能证明设计动机；后者需 ADR、原要求或用户确认。

**可执行的示例与步骤。** 复用服务、浏览器和任务包运行安装、API 和迁移示例。优先使用项目已有 doctest、测试或文档生成器，而非自建通用执行器；每项示例明确输入、预期输出、环境和副作用。导入模块可能执行副作用，Sphinx autodoc 就明确存在这类边界，必须在授权的隔离环境运行。[Python doctest](https://docs.python.org/3/library/doctest.html)、[Sphinx autodoc](https://www.sphinx-doc.org/en/master/usage/extensions/autodoc.html)

**跨文档一致性。** 找同一接口/术语/版本在 README、API 参考、迁移指南和排障手册中的冲突。确定的版本/命令矛盾可自动检查，语义取舍仍标建议。检查应能容纳明确的 v1/v2 历史章节，不能把历史说明误当成错误后统一改写。

**代码与文档共同更新。** diff 先确定受影响代码和文档声明，再给出段落级修改、来源和需要重验的示例。只读到代码不足以宣称文档已完整维护；交付显示没有覆盖的声明、失效示例和缺失读者路径。需要大改时可以做两套结构小试验，但最终仍用同一读者任务验收。

**版本和交付质量。** 文档、来源、示例结果和所对应代码版本形成一个产物版本。复用当前预览/下载和不可变存储，后续按需要接 Markdown/HTML/PDF/DOCX 等适配；检查链接、目录、表格、代码块和渲染。导出成功不等于可读，PDF/Word 等需实际渲染核对；本轮没有提前实现这些出口。

### 6.3 独立插件形态

未来可增加可选文档领域模块，管理声明来源、示例计划、文档变更建议和版本记录；Pi 扩展提供按需工具与命令，现有 Web 工作台展示声明/证据/差异。主 Agent 仍使用 Pi 模型循环和会话树；对其他 Agent 保留 Markdown/JSON 的可核对出口。不会改 Pi 内核或强迫基础 coding 任务加载全部文档工具。

第一轮建议用真实三仓库 API 迁移生成并维护指南，包含故意过期的字段、失效命令和不成立的设计理由。验收由未参与写作的人或独立流程照文档完成升级，保留原工程检查。度量无来源声明、示例执行结果、冲突漏检、实际读者完成情况和维护总成本。自动检查覆盖和写作质量分别表达，不靠一名模型的自评分宣布完成。

## 7. 实施取舍与验证顺序

| 次序 | 建议未来交付 | 进入下一步的依据 | 暂缓内容 |
|---|---|---|---|
| 1 | 关键假设小实验、带条件失败记录、简短完成凭据 | 同目标对照任务减少返工且原验收保持，前置成本可解释 | 固定角色流水线、每轮自动反思 |
| 2 | 文档来源声明和可执行迁移步骤 | 同一三仓库指南可被独立执行，源码变化使旧声明失效 | 通用排版平台、全部格式一次实现 |
| 3 | 跨文档一致性与段落维护 | 版本冲突能发现，历史版本不被误改，实际维护成本下降 | 仅根据代码编造设计理由 |
| 4 | 只观察和有界运行恢复 | 影子建议的误报可接受，旧执行终态与原要求可靠 | 任意内核热修、凭超时全代码回滚 |
| 5 | 按复用价值的空闲整理、差量交接 | 后续任务实际使用这些成果，总成本得到核对 | 无限制做梦、全量覆盖长期记忆 |

这些次序不是新 Goal 的授权。下一阶段应选择一个具体用户问题和原成功标准，完成可否定试验后再扩展，不为每个点子立即创建插件。时光机的妙处是降低试错代价；新的机制也应改变一次真实工作中最容易浪费时间或丢失事实的环节。

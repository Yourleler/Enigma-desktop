# Enigma-next 实施计划

确认日期：2026-10-24，Asia/Shanghai。

## 产品定位

以个人日常可用的 coding agent 为基础，重点强化多仓库理解与协同改造。Pi 提供通用底座，Enigma-next 实现领域增量。仓库独立于现有 Enigma Python 稳定版。

## 1. 多仓库协同

- 一个任务管理多个独立仓库，支持运行中加入仓库。
- 明确每个仓库的位置、分支、基线、角色和操作范围。
- 分析仓库之间的依赖及变更影响，协调修改顺序。
- 同时执行各仓库检查及跨仓库联合验证。
- 通过至少三个独立仓库的案例证明数量可扩展，不把能力限定为双仓库。

## 2. 智能代码阅读

- 围绕用户问题追踪“入口—接口—实现—调用方—测试”，支持跨仓库。
- 阅读结论关联真实源码位置与版本，区分确定关系和推测关系。
- 按需展开结构、关键代码和说明，避免每次扫描并总结所有代码。
- 根据多仓库工程任务独立设计数据模型与实现；不纳入第三方私有源码、提示词、内部协议或内部服务依赖。

## 3. 基于 Pi 会话树的时光机

- 将任务检查点关联到各仓库代码快照、阅读结果和验证记录。
- 支持方案分支、比较和恢复，保留原分支及完整执行记录。
- 区分上下文切换和代码恢复，只在完整工具执行结束后切换。
- 保护用户原有修改，保留最新要求、权限及累计预算。
- 切换后核对实际代码状态，过期阅读结果与测试记录重新检查。
- 处理中断、未知执行结果和部分恢复，避免重复副作用或误报恢复成功。

## 辅助能力与简化范围

保留实际产物检查、测试、联合验收以及必要操作约束和日志脱敏。计划、进度和恢复优先复用 Pi。

第一版不自建长期记忆/中文召回、独立通用审查系统、固定四角色流水线或频繁自动反思。环境诊断按实际需要接入。

## 实施顺序

1. 固定 Pi 依赖并接通公开扩展、SDK 和可运行入口，验证个人基础 coding 流程。
2. 建立多仓库工作区、任务清单和联合检查，覆盖运行中新增仓库。
3. 实现按需代码阅读，先验证真实源码追踪，再扩展跨仓库关系。
4. 关联会话节点与仓库快照，完成分支比较、代码恢复及状态一致性检查。
5. 使用真实工程任务验收，补全安装、运行、测试和架构文档。

步骤可以根据实际依赖调整，但不以接口演示或最小样例替代完整目标。

## 验收要求

- 通过 Pi 完成实际文件读写、命令执行和基础 coding 任务。
- 至少三个独立仓库能围绕同一目标联动修改，分别验证并联合验收。
- 代码阅读能指向对应版本的真实源码，未确认关系不会被当作确定事实。
- 分支切换保留原历史，代码恢复保护原有修改；切换和恢复后的工作区、阅读结论及检查状态一致。
- 拒绝操作、取消、中断和未知执行结果有正确处理，不重复执行不确定的副作用。
- 文档提供可复现的安装、运行和验证方法。
- 明确区分受控模型测试与真实模型验证；没有真实模型证据时不宣称真实 coding 效果。

## 研究依据

- [Pi 扩展接口](https://github.com/earendil-works/pi/blob/v1.4.0/packages/coding-agent/docs/extensions.md)：工具、生命周期与领域状态接入。
- [Pi 会话树](https://github.com/earendil-works/pi/blob/v1.4.0/packages/coding-agent/docs/session-format.md)：分支和上下文投影；会话切换不能替代文件系统恢复。
- [Kimi 状态一致撤销修复](https://github.com/MoonshotAI/kimi-code/pull/2055)：回退上下文时，Todo、计划和后台通知也需协调；外部世界状态与累计运行状态需分别处理。

这些资料证明相关接口或问题存在，不构成 Enigma-next 已实现能力或效果的证明。

# 从实际困难出发的 Agent 新机制候选

研究日期：2026-10-25。本文为头脑风暴与未来计划，不授权实现新功能。主升级完成后的最终创新与文档专精计划仍按既有安排单独交付；本文可作为其研究材料。

## 1. 哪些点子已经存在

时光机的价值是保留探索机会和恢复错误状态，做梦的价值是将跨会话经验与上下文的处理移到更合适的时机。做梦可以整理记忆，也可以预先理解资料、建立有用表示或准备多个相关问题；“在空闲时做”与“总成本更低”是两个需要分别验证的命题。

| 现实问题 | 已核实的公开方案 | 尚值得研究的增量 |
|---|---|---|
| 走错修改路线 | Claude Code 检查点；LangGraph 回放/分叉；Pi 会话树 | 跨仓库代码、最新要求、计划、通知和证据的一致恢复，以及外部副作用边界。[Claude](https://code.claude.com/docs/en/checkpointing)、[LangGraph](https://docs.langchain.com/oss/python/langgraph/use-time-travel) |
| 每次临场重新理解长期资料 | Letta sleep-time agents；LangChain 背景记忆更新 | 只整理有后续价值的材料、按变化失效、控制总成本和隐私。[Letta](https://www.letta.com/blog/sleep-time-compute/)、[LangChain](https://docs.langchain.com/oss/python/concepts/memory) |
| 不断重复而不推进 | Magentic-One 进展检查与重新规划；Gemini CLI 循环检测 | 以实际变化和证据验证纠偏效果，并跨进程处理宿主故障。[Magentic-One](https://microsoft.github.io/autogen/stable/user-guide/agentchat-user-guide/magentic-one.html)、[Gemini](https://github.com/google-gemini/gemini-cli/blob/main/packages/core/src/services/loopDetectionService.ts) |
| 执行中偏离要求、重复低效尝试 | Wink 异步轨迹观察与纠偏提示 | 连接行为建议、执行控制和跨仓库恢复；提示被采纳不等于原任务通过验收。[2026 年原论文](https://arxiv.org/html/2602.17037v2/) |
| 经验总结越来越短、遗漏有效细节 | ACE 以结构化增量更新整理策略；Reflexion 将任务反馈形成情景记忆 | 有版本的失败适用条件、冲突/失效记录和真实使用效果，避免全量覆盖记忆。[ACE](https://arxiv.org/html/2510.04618v2)、[Reflexion](https://proceedings.neurips.cc/paper_files/paper/2023/hash/1b44b878bb782e6954cd888628510e90-Abstract-Conference.html) |
| 某轮失败后无法继续 | 持久检查点、节点超时、重试和错误处理；Codex 的目标/状态/压缩/取消接口 | 正确处理执行静止、世界状态和验证覆盖，形成个人工具的统一使用流程。[LangGraph](https://docs.langchain.com/oss/python/langgraph/fault-tolerance)、[Codex](https://learn.chatgpt.com/docs/app-server) |
| 上下文变大导致慢或溢出 | Pi 压缩；OpenAI 服务器端或独立压缩；Claude 压缩 hooks | 压缩前后核对任务约束和证据，不让顺畅续跑掩盖遗漏。[OpenAI](https://developers.openai.com/api/docs/guides/compaction)、[Claude](https://code.claude.com/docs/en/hooks) |

因此，“大众 Agent 都没做”不成立于这些基础机制。是否有产品覆盖完整组合、默认启用且在复杂个人项目中可靠，现有核读不能给出全市场结论。候选创新应围绕尚未解决的具体使用问题，而不以换名字或再加一个模型会话作为创新证明。

时光机、做梦、失败经验和旁路纠偏已有公开机制；具体产品的覆盖、默认行为与可靠性是另一个问题。本项目的优先价值应是把个人多仓库任务中的“走错、卡住、忘记、无法取证、难以续接”串成可解释的工作流程。下列候选是设计提案，没有宣称世界首创。

Sleep-time Compute 的原始研究在特定的有状态推理任务上研究预计算收益，不能直接外推为 coding agent 的普遍提速。[原论文](https://arxiv.org/abs/2504.13171) Enigma-next 现有的小规模记忆对照也没有显示更快，后续应继续比较完整成本与实际任务价值。本地对照（本地参考文件）

## 2. 候选点子

以下均是提案。优先级是对当前个人多仓库方向的判断，不是已验证效果；“已有基础”也不代表新增机制已经实现。

| 候选 | 解决的实际困难与用法 | 已有基础与建议增量 | 主要失败风险 / 验证方法 | 优先级 |
|---|---|---|---|---|
| **先验证关键假设** | 改一堆代码后才发现版本、接口或运行入口猜错。开始前选最影响方案的少量假设，做最小取证实验 | 复用源码阅读和证据；为关键假设记录来源、确认状态和依赖的下一步，不强迫所有任务填表 | 错误实验确认了错误前提；比较后续返工、真实漏项和前置开销 | 高 |
| **记住失败的适用条件** | Agent 经常重试同一条已失败路线。记录“在这个版本、配置、错误下，此法失败”，换上下文后先检查 | 复用记忆与观察；增加失败条件和失效规则，区别于永久禁止某方法 | 旧失败阻止后来正确做法；用版本改变后应解除的案例测试 | 高 |
| **把不同方案做成小实验** | 大改之后才知道方案不适合。先在独立分支验证难点，用同一成功标准比较，再选方案 | 复用时光机、分支和联合检查；增加实验成本、结论来源与被放弃理由 | 实验省略真正难的集成环节；必须包含风险最大的真实路径 | 高 |
| **任务约束在压缩前后对账** | 会话越长越容易遗漏“不能改”“必须验”“只研究”等限制 | 复用原始要求与计划；压缩前后核对要求标识和验收清单，缺项回读原文 | 自动摘要误认约束变更；始终以原始用户输入和当前明确要求为依据 | 高 |
| **先确定长任务如何取得终态** | 启动构建/CI 后才发现没有查询接口，最后长期猜测 | 复用观察/后台能力；启动前明确结果来源、失败信号和取证备用路径 | “有通知”被误认成“有结果”；注入丢事件、过期授权与来源不明测试 | 高 |
| **保留原标准的分层验证** | 检查太贵导致无限等待，或用一个小测试掩盖未验证部分 | 复用验收证据；先运行有价值的局部检查，清楚列出仍需执行的完整检查 | 偷换成功标准；原检查版本固定，未覆盖项目始终可见 | 高 |
| **只做有后续价值的后台整理** | 空闲整理大量资料，用户回来发现成本更高而内容用不上 | 复用按需记忆；按复用频率和变化情况挑选材料，先小批整理，主任务恢复后让路 | 预测错后续任务、抢占模型资源或造成记忆污染；记录整理成本、实际召回/采纳与旧信息失效 | 中 |
| **按时效重新核对外部环境** | 昨天的接口、凭证、运行方式今天已变；旧知识还在指导行动 | 复用来源/hash 与配置观察；给外部事实设置核实条件，变化时提示相关计划与资料 | 把短暂故障当成永久变化；区分可恢复失败与事实改变 | 中 |
| **减少切换任务后的重建成本** | 隔几天回来，只记得“改过一些东西”，不知道从哪继续 | 复用交接包与产物；给出最近目标、未解问题、有效证据、最小下一步及变化提醒 | 把过期小结当真；恢复时核对当前代码、配置与权限 | 中 |
| **为完成的工作保留可核对说明** | 代码完成但设计/API/排障文档很快过时，下一轮再次摸索 | 复用源码地图和资料版本；维护文档声明与源码/验证的关联，只建议更新受影响内容 | 自动写作编造因果或示例；用来源定位、实际命令与跨文档检查验证 | 中，纳入后续文档专精评估 |

## 3. 值得进一步建模的机制

相比继续堆工具，下列机制围绕一次真实困难改变工作顺序。它们不在本轮实现范围，效果需要未来对照试验。

### 3.1 等待关系图：回答“到底在等谁”

不只显示“工具运行 20 分钟”，而是记录“浏览器在等前端，前端在等后端就绪，后端在等凭证”；再标出哪个条件由 Agent、外部系统或用户产生。主进程活着但依赖事件永远不会来时，运行期限只是最后的兜底。

未来增量是为阶段记录期待事件和产生者，识别已经失去产生者的等待、任务间循环等待与缺少终态通道，并建议最小调查。当前服务依赖图和等待记录可作基础，但尚未覆盖主 Agent 全部阶段。错误依赖可能制造假死锁，因此仅有推测边不能触发硬取消。

### 3.2 小实验优先：把不确定性变成下一步

例如，跨三仓库接口升级存在两个假设：“旧调用方还能解析新字段”“新服务可在本地跑”。先验证最能推翻方案的假设，再投入大改；不要求每个小任务增加一轮规划。实验必须有能否定方案的结果，模型自信和阅读结论不足以替代运行。

当前源码阅读、契约与分支检查可复用。未来增加假设的适用版本、判据、影响步骤和失败后的备选路线，并比较返工减少是否超过前置成本。这与既有反思研究相邻，增量在于把经验落实到可执行的下一次取证动作，而不是再写一段总结。[反馈驱动试验的研究基础](https://proceedings.neurips.cc/paper_files/paper/2023/hash/1b44b878bb782e6954cd888628510e90-Abstract-Conference.html)

### 3.3 回溯带走教训：代码退回，失败条件留下

只回滚代码可能让 Agent 重新踏入同一条路。建议将被放弃路线的事实留在分支外：在哪个源码/配置版本、哪个验证下失败，哪些后续步骤依赖了这个错误假设。恢复后的主 Agent 按需看到这些事实；新版本解除旧限制，用户也可推翻结论。

记忆条目应以局部增量更新，而非每次做梦把整本经验覆盖成更短摘要。ACE 提供了上下文增量整理的研究先例，但它的基准结果不证明这里的跨仓库条件记忆一定有效。[ACE 原论文](https://arxiv.org/html/2510.04618v2) 本项目的未来试验应包含“旧方法后来变正确”和“当时只因凭证失效”的反例。

### 3.4 验收债务与完成凭据：不要把失联变成结束

把原要求到检查、检查到实际证据、证据到版本的关系保持可见。CI 的通知丢了、测试超时了、浏览器没执行时，任务可以继续做独立工作，但这些项目始终是未结算验收。完成时输出能回查的简短凭据，说明哪些要求有证据，哪些仍未知。

当前检查证据和任务地图已有基础。未来需要把压缩、交接、分支恢复和托管干预后的缺口一起保存，防止新的会话将“上个 Agent 说通过”当作新证据。独立检查与模型判断分别呈现；管家没有权限消除原要求。

### 3.5 差量交接：新对话不必重读全部历史

交接时分别提取共同背景、本次新目标、未解假设、可用证据和明确禁止带走的权限/私密材料。目标 Agent 接手后先对账源码与材料版本，再只补发生变化的部分。这样同背景新任务可以复用知识，同时不自动继续旧 Goal。

当前交接包支持基础来源与版本核对；未来可研究接收端问题驱动的补充取证和资料变更摘要。所谓“转到任何 Agent”受其公开输入、工具和权限模型限制，不能保证完整迁移隐藏状态。价值应按重复描述时间、过期背景采纳和遗漏要求衡量。

### 3.6 文档维护作为专精：让说明跟着事实变

把文档中的接口声明、配置解释、迁移步骤和可执行示例关联到源码与验收。代码变化后只找受影响的声明，给出需要重验/重写的段落；涉及跨仓库协议时，同时核对服务、SDK、调用方和文档版本。

它比自动润色更贴近当前多仓库方向，也有实际维护价值。当前材料、阅读、产物与联合检查可复用；未来需增加声明来源与示例执行验证，并尊重文档里的取舍说明不能从代码自动推出。完整实现结束后，最终专精文档再比较文档维护、迁移协作与其他候选，不提前确定产品方向。

## 4. 与托管管家的组合

第一、二、四项减少走错路线；第五、六项减少无法观察和无法验收的停滞；独立管家处理运行中故障；后台整理帮助下一次任务开始。这些机制可以共享同一套来源与证据，但应分别启用和记录成本，避免变成固定多角色流水线。

例如，关键假设实验失败后留下带版本的负面经验；长验证超限时，管家先确认状态，再提出覆盖关系明确的替代尝试；换方案后仍保留原要求和未覆盖项。这样的闭环有较明确的个人使用价值，具体实现与误判率仍需试验。[托管分析](supervised-mode-feasibility.md)

## 5. 暂缓的方向

任意自改 Agent 内核、自动放宽验收、无限派生监督 Agent、频繁全量反思、凭超时立即回滚全部代码，都缺少清楚的收益与停止条件。可以保留为研究问题，当前更值得先探索范围明确、可逆、有来源、能够被真实案例否定的机制。

托管和做梦需要比较“整个工作完成的成本与质量”，不能只看前台等待时间。评估应保留正常长任务的误杀、重复副作用、遗漏需求、陈旧记忆采纳、用户介入次数和总模型/基础设施开销。本文没有为这些候选编造收益数字。

本次追加核读的原始材料见 `manifest-4.json`、`manifest-5.json`。Wink 的异常纠偏、ACE 的记忆整理和 Reflexion 的反馈记忆各自只构成其机制与实验范围的证据，没有完成在统一 Pi 故障集上的比较。后续优先建议研究“关键假设小实验 + 带条件的失败记忆 + 完成凭据”，再引入有界托管恢复；它们能服务同一个多仓库工程任务，也分别具有可否定的验收方法。

## 6. 将点子落到可验证的使用收益

最有价值的候选不是继续增加 Agent 数量，而是让现有任务少做一次错误的大改、少重复一次失败尝试、少丢一项原要求。下面是设计判断，尚无本项目的对照效果数据，也不主张其他产品从未做过。

| 机制 | 具体触发场景 | 建议新增的关键动作 | 可否定这项设计的反例 |
|---|---|---|---|
| 先取证再押注 | 多仓库协议有两个解释，任选一个都会影响大量代码 | 找出能区分解释的最小真实实验；结果绑定来源版本，后续变更沿已确认前提展开 | 前置实验耗时超过返工收益，或小实验绕过真实集成难点 |
| 回溯保留失败条件 | 退回旧节点后又尝试同一条失败路线 | 代码与方案回退，保留“在这些条件下失败”的事实；条件改变后重新开放尝试 | 旧故障只是短暂断网，却被记成永久禁用方法 |
| 等待前先确定终态渠道 | CI、远端构建或长工具发起后无法获取结果 | 先确定结果标识、查询路径和备用观测；缺渠道时先补采集或明确验收债务 | 建了通知通道，但无法证明收到的是本次运行的终态 |
| 压缩与交接的约束对账 | 很长的任务经过压缩、Fork 或跨 Agent 转移 | 对账原要求、最新更新、未验项目和未结算效果；发现缺项回读来源 | 错误摘要被用来反向修改原要求，使对账形式通过而实际漏项 |
| 按依赖恢复最少状态 | 一项操作出错，直接全回滚丢掉正确成果 | 建议先修展示、重试请求或重做验证；需要代码恢复时核对受影响依赖与用户改动 | 依赖图漏边，局部回滚留下跨仓库不一致 |
| 干预后的独立确认 | 管家做完恢复，主 Agent 开始输出便宣布救活 | 同时核对原故障、原验收和新副作用；失败停止重复恢复并给出可接管记录 | 只测重启率，遗漏误杀正常任务、重复写入和最终失败 |

这些机制可以形成一个场景闭环：协议假设的小实验失败，留下有版本的失败条件；切换方案时保留这些条件；长联合验证开始前准备终态取证；验证器故障时只恢复验证层；压缩或交接后仍显示原检查未结算。与时光机和做梦同样，价值来自改变工作顺序和信息保存时机，而不是给现有日志换一个名字。[恢复边界](supervised-mode-feasibility.md)

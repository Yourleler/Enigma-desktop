# 记忆的实际效用对照

本轮使用现有 Gateway `gateway-gpt-6-1-sol`，同一三仓库 Python/JS 项目与明确的既有文档约定，分别完成接口文档和消费链文档两个任务。比较方式：前文直接提供原始约定、不建立记忆；工具按需读取原始约定；轻量记忆搜索与正文读取。三种方式拥有相同的源码发现、读取与写入能力。

| 方式 | 接口文档耗时 | 消费链文档耗时 | 实际结果 |
|---|---:|---:|---|
| 原始约定直接在上下文 | 13.97 秒 | 17.80 秒 | 两项成功 |
| 按需读取原始历史 | 17.42 秒 | 14.31 秒 | 两项成功 |
| 轻量记忆索引与正文 | 17.99 秒 | 17.58 秒 | 两项成功 |

成功定义：实际文档使用用户此前指定的 `GREETING-CONTRACT` 名称、描述当前响应的 message 字段，API 源码保持原结构。各次任务均保存物理文档和原生会话，索引与正文建库总耗时约 16.64 ms，没有额外提炼模型请求。工具轨迹、输入/输出/cache usage 和服务端报告的 cost 字段写入报告；这些 cost 不能当作已确认的账单金额。

这组数据没有证明记忆能减少耗时；可见价值是跨会话按需找到既有项目约定，但对于较短背景，直接给上下文或读取原文同样有效。因此插件保持按需，向量检索和复杂自动反思没有被默认加入。

范围限制：每格一次运行、两类小任务，顺序执行且文档输出逐步累积，环境/缓存/模型随机性没有独立控制。不能推断长期成本、成功率或因果收益，也不能将这份结果外推到大代码库。

初版实验工具列表遗漏文件枚举，模型猜路径、23 次文件读取失败并未产出文档。该失败单独保留，不计作任何记忆策略的效用；修复共同的文件发现工具后才完成上述对照。

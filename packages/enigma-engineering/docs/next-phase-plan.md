# Enigma-next 下一阶段方案

评估日期：2026-10-25，Asia/Shanghai。原基线为 0.1.1，提交 `117f4c3`。本文保留设计与取舍，实施已推进至 0.2.0，当前行为与证据见 [版本说明](release-0.2.0.md)和[实施进度](upgrade-progress.md)，不要把下文历史缺口当成已验证状态。

## 定位与宿主选择

专精方向是个人多仓库协同改造：围绕一个实际需求，理解跨项目接口和依赖，协调修改，联合验证，并比较不同方案。个人 coding agent 的模型调用、工具循环、对话、压缩和界面继续复用成熟宿主。

建议先交付规范的 Pi 插件包，并使领域逻辑独立于宿主。当前实现使用 Pi 公开扩展，没有修改 Pi 内核；扩展加入工具、工作流和领域状态符合 Pi 的设计。Pi 官方明确将这类定制定位为扩展，并提供分支状态、工具审批和生命周期示例。[Pi 扩展文档](https://github.com/earendil-works/pi/blob/v1.4.0/packages/coding-agent/docs/extensions.md)

不过当前还不是边界清晰的通用插件包：`workspace.ts` 为 code fork 直接读取 Pi 会话；扩展启动时覆盖活动工具集；验收和当前用户要求的保护与宿主事件集中在一个工厂内。下一轮应移动这些具体耦合，不引入通用运行时框架。

推荐结构：领域能力（仓库、阅读、变更、证据、恢复）→ 薄 Pi 适配层 → Pi 原生执行与界面。领域层接收明确的会话来源、要求引用和操作结果，不解析宿主会话格式。CLI 可以继续作为便捷启动入口，插件也应能按官方方式独立加载和移除。

插件分发遵守 Pi package manifest 和宿主依赖约定；现有一体化启动器携带 Pi 依赖本身不是违规，改为可安装扩展后应避免重复携带宿主模块。普通加载不能无条件覆盖用户已有工具集；受管协同模式需显式启用，并覆盖该模式实际可达的写入与命令路径，不能因留下原生工具而绕过领域记录。[Pi 包规范](https://github.com/earendil-works/pi/blob/v1.4.0/packages/coding-agent/docs/packages.md)

DSH 的插件树、工具执行管线、文件系统/进程 provider、Web/SDK 宿主具有吸引力，适合进一步组合执行环境与产品界面。但截至本次评估，最新发布为 `0.2.1-rc.3`，官方仍声明开发预览和破坏性变更。[最新发行](https://github.com/deepseek-ai/deepseek-harness/releases/tag/dsh-v0.2.1-rc.3)、[架构](https://github.com/deepseek-ai/deepseek-harness/blob/dsh-v0.2.1-rc.3/docs/architecture.md)、[README](https://github.com/deepseek-ai/deepseek-harness/blob/dsh-v0.2.1-rc.3/README.md)

迁移不会自动解决领域持久化和代码恢复：DSH 会话文档明确禁止仓库外插件调用 `appendPluginRecord`，其内部实验性记录的格式迁移也是尽力保留；自有状态必须使用允许的接口或领域存储，并实际证明重启、分支和兼容行为。DSH 的进程沙箱模式只约束文件效果，网络和进程可见性不在该模式承诺内。[会话接口约束](https://github.com/deepseek-ai/deepseek-harness/blob/dsh-v0.2.1-rc.3/packages/core/session/README.md)、[沙箱边界](https://github.com/deepseek-ai/deepseek-harness/blob/dsh-v0.2.1-rc.3/docs/subsystems/sandbox.md)

只有下一阶段出现经验证的 Pi 公开接口缺口，或明确需要 DSH 的 Web、远程执行与管线组合收益，才做一个受限的 DSH 外部插件试验。验证 Gateway 调用、多仓库工具、取消后的执行结束、领域状态的重启与分支关联、安装和移除，再记录迁移收益与代价。通过后迁移一个主要宿主；不同时维护两个完整产品。



| 要素 | 在 Enigma-next 中的用途 | 本轮边界 |
|---|---|---|
| 按任务组织代码地图 | 将入口、接口、实现、调用方、测试与跨仓库影响串联，可展开到源码 | 明确源码事实、静态候选和模型推断；不先建设全仓库知识图谱 |
| 版本一致的阅读产物 | 新分析未完成时保留可查看的旧结果，并标明旧版本；最终结果引用对应代码 | 已修改文件及必要依赖决定失效范围，无法确认时扩大范围 |
| 变更来源与增量审查 | 分别查看整体工作区变化、受管工具记录的变化，以及外部或来源不明变化 | 命令同时影响多仓库时如实记录观察范围；无充分证据不宣称精确作者归因 |
| 有依赖的轻量任务计划 | 表达仓库责任、前置产物、验收项、阻塞原因；上游接口变化使下游结果重新待验 | 先单 Agent 顺序执行，有界并行仅用于已证明独立的操作；不自建企业工作流平台 |
| 按需独立审查与交接 | 使用独立审查上下文检查实际新增 diff、目标与验收证据，结论绑定原任务和版本 | 默认关闭；优先宿主公开能力；不预设四角色流水线，不共享可变计划状态 |

这些参考不作为实现来源；不复制源码、提示词、内部协议或内部服务依赖。也不迁入企业审批、组织权限、云调度、消息系统、模型路由平台或通用长期记忆平台。按用户新增要求加入的小型记忆插件见下文增补方案。

## 三条重点流程

1. **需求到联合验收**：从用户问题生成有源码依据的影响子图，找到应修改的仓库和契约，形成轻量计划；修改后选择相关单仓库和跨仓库检查，并解释覆盖范围与缺口。依赖不明时允许用户补充或保守扩大范围。
2. **修改到增量阅读**：已有 TS/JS 阅读器接入真实项目配置与可靠符号解析；新增一种语言支持，优先 Python 或 Go，用实际跨语言案例决定。只对有证据的关系作确定陈述，测试同名符号、导入别名、重导出和无法解析情况，避免把文本命中当成调用关系。
3. **方案到可比较的恢复**：将轻量计划、代码版本、阅读结果和检查状态关联会话节点。上下文导航与代码恢复继续分开；方案比较显示 diff、受影响仓库、有效检查及缺口。恢复前预览，保护用户修改、最新要求、权限和累计消耗；分支切换后重新核对当前状态。

时光机同时协调领域状态，不能只撤回对话。新 code fork 需要可用的会话来源和要求交接，目前仅有来源记录，不等于已复制整个会话。只有公开接口允许且经验证后，才把原生会话分支与新工作区的启动流程接成完整操作。[Pi 会话树](https://github.com/earendil-works/pi/blob/v1.4.0/packages/coding-agent/docs/session-format.md)、[Kimi 状态一致撤销问题与修复](https://github.com/MoonshotAI/kimi-code/pull/2055)

## 实施顺序与验收

先保存并验证现有基线，再整理插件与领域边界，然后依次补齐协同计划、代码阅读、方案比较与恢复，最后接入按需审查。2026-10-25 用户追加记忆和慢运行诊断：并入下面的观察与记忆插件步骤，先建立耗时和进展证据，再交付按需知识复用与有依据的性能优化。保留实际检查、必要权限和脱敏。

验收以完整真实任务为准：至少三个独立仓库围绕同一需求变更，含上游契约、下游消费者与真实联合检查；至少一个跨语言案例。测试运行中新增仓库、用户同期修改、源码变化使阅读失效、上游变化使下游验收失效、取消、强杀、部分恢复，以及最新要求在旧分支继续生效。

插件验证涵盖原生 Pi 加载和移除、与另一无关扩展共存、显式受管模式、恢复后领域状态一致；不要把正常关闭界面误判成任务验收失败。

继续使用已接通的 Gateway 作真实模型验证，不改当前 Codex/Gateway 凭证和服务。运行适用的静态检查、回归与跨平台 CI；真实效果、受控测试和未覆盖条件分别记录。最终交付可复现命令、证据、边界、安装文档与可审查提交。不能用源码行数或绿色单测替代能力验收。

## 用户新增范围：记忆与运行观察

按 [记忆与运行观察方案](memory-observer-plan.md)实现两个可选插件：按需、带来源/版本/适用条件的知识记忆，以及主任务运行期间可独立查询的观察旁路。观察结果驱动阶段耗时优化和困难时的经验召回。支持个人、项目、仓库关系及任务方案，覆盖代码之外的稳定偏好和可复用研究知识，避免记忆污染、陈旧信息、频繁自动反思和索引依赖导致阻塞。

新增能力必须完成该方案的六组验收，与原三仓库、跨语言、恢复、审查和真实 Gateway 验收一同计入当前 Goal 的完成标准。

# Enigma-desktop

面向个人工程项目的桌面 AI 助手。重点是**多仓库协同、代码智能阅读、可靠的长任务接续，以及代码与文档共同维护**。

基于 [OpenHanako / HanaAgent](https://github.com/liliMozi/openhanako) 的桌面与 Web 宿主，底层使用 **Pi 1.4.0**。工程增量通过领域模块、插件和必要的宿主适配接入，复用同一主会话与 Agent Loop。

本文同时作为项目入口和工作交接说明：保留最终使用目标，区分已有实现、已取得的验证和剩余工作。逐轮版本记录见[完整验收清单](docs/full-feature-acceptance-2026-10-31.md)。

## 2. 快速开始

### 已有应用

打开本地安装的 **Enigma.app**。本机工作台直接进入，无需设置工作台密码；远端访问使用配对机制。

在“设置 → 供应商”配置模型，再选择默认对话模型。兼容 API 可以继续使用，Ollama 是可选后端。模型名称、可用能力和连接状态以当前配置及实际验证为准。

### 从源码运行

需要 Node.js **`>=24.12.0 <25`**。以下命令均在仓库根目录执行。

```bash
npm ci
```

桌面开发入口：

```bash
npm run build:client
npm run enigma:desktop
```

Web 开发入口：

```bash
npm run enigma:web
```

服务就绪后，在另一个终端打开工作台：

```bash
npm run enigma:open
```

服务端口由启动时分配，不应把历史演示端口写成固定地址。

### 数据与模型配置

| 用途 | 默认位置或入口 |
| --- | --- |
| 已打包应用数据 | `~/.enigma-desktop` |
| `enigma:*` 开发入口数据 | `~/.enigma-desktop-dev` |
| 指定隔离数据目录 | 环境变量 `ENIGMA_DESKTOP_DATA` |
| 新开发配置的默认工作目录 | `ENIGMA_DESKTOP_WORKSPACE`，或启动脚本的 `--workspace` 参数 |
| 显式导入 Pi 模型配置 | `node scripts/launch-enigma.mjs server --models /path/to/models.json` |

`/path/to/models.json` 是待替换的示例路径。导入会合并供应商目录，并在数据目录内保留迁移备份；已有配置优先保留。不要将密钥、模型配置或个人会话放入源码仓库。

正常自我介绍会保留身份、性格、职责和能力说明，并加上寄语：`I'll be your enigma,We could be anything you want.`。这句话不替代原有介绍或其他设定。251补齐旧对话恢复路径：仅替换已知旧宿主首行，保留所有后续人格和能力内容。底层平台介绍不再主动附加；公开技术来源与许可仍保留在文档中。

开发目录与正式应用目录相互独立：在开发入口看不到正式配置，不代表正式模型或会话被删除。上游通用启动脚本有自己的默认目录，开发本项目优先使用上面的 `enigma:*` 入口。

| 能力 | 最终使用目标与期望效果 | 当前实现与边界 |

| 任务编排管家 | 用户交代目标和限制后，由特殊对话组织项目与多个工作对话，安排依赖、并发、模型、整合和统一验收 | 已有真实并发、隔离成果、权限收紧、取消接续与原检查；管家和受管工作对话可往返。通用协作助手定位与切换时的响应隔离已补验，复杂编排继续核对 |

时光机借鉴的是带着教训调整上下文路线。**回溯上下文不会自动撤销文件，更不能撤销已经发生的外部操作。** 代码恢复、任务重试、组件维修各自核对范围与结果，不能借回溯清零预算、隐藏失败或重放效果未知的写入。

托管需要保留原验收要求。某个验证方法过慢，可以调查替代路径或调整顺序，但未满足的原条件仍是缺口。组件维修先在隔离副本复现、修复和验证，不对运行中的内核作无约束修改。

管家初期管理自己创建和拥有的工作对话；管理既有对话或外部 Agent 时，仍需明确所有权与授权。工人报告“完成”不代表父目标已经验收。

## 4. 界面与交互要求

### 项目、对话与工作目录

- **普通对话**可以独立存在，不必归属项目。
- **项目**组织多个对话、共享说明、笔记与授权目录。项目和最近对话在同一侧栏层级，各分组及项目下属对话可折叠；下属对话需要明确缩进。
- **工作目录**是本次操作文件或命令的落点，不等于项目本身。项目可以先不关联目录；涉及文件时再选择对应目录与权限。
- **多仓库**是一个项目中的多个协作目录，各自记录职责和权限，不要求用一个 Git 仓库包住全部内容。
- **旁路**回答运行状态；**托管守护**监督执行与有限恢复；**任务编排管家**组织多个工作对话。三者可以组合，但不是同一个按钮的不同名字。

项目与对话的置顶、归档、归属和设置靠近左侧条目，低频操作按需显示；设置入口位于左下角。目录名称应可打开对应位置，不用内部 ID 代替面向用户的名称。

### 布局与材质

- 顶部保持一条工具栏，与左侧外框贯通；中间对话及左右侧栏使用统一的内容材质，外框略通透，内容区域略厚。
- 左右侧栏独立收放，空间足够时可同时展开；窄窗按空间让位。顶部分隔短线与下方侧栏边界同步，拖动不滞后。
- 右侧以文件、变更、浏览器、任务和独立预览标签组织内容。标签可关闭、从加号恢复、拖动调序；拖动显示落点和动态让位。
- 文件列表点开的预览留在同一文件面板；聊天链接、导入或固定的文件可成为同级标签。列表与预览可调整宽度，搜索、帮助和复制对象必须清楚。
- 标签溢出用模糊渐隐与方向箭头提示，避免硬切文字；滚动不切换面板，点选不意外调序。
- 深色以近黑和绿色主导的多色极光为主，也可选光环或纯色；浅色以白色和淡紫为主，可选光带、不规则大理石或纯色。深浅分别记住背景。
- 玻璃、背景和动效分别控制。清晰度覆盖顶栏、侧栏、对话、输入框和 Token 控件；扩大厚材质端的范围，保留最强液态玻璃端点。
- 按钮默认融入界面，悬停、聚焦、按下和选中状态清楚；提示、字号、间距、图标和圆角统一。默认图标采用几何风格，用户自定义头像保留。

### 输入、历史与用量

- 快速聊天有可见关闭按钮和Esc收起，保留未发送内容；外侧透明、正文区域采用更清晰的磨砂底色，不在后台并排留下同名测试浮窗。
- 图像和文件可插在正文指代的位置，形成“文字［图片］文字”；展开编辑不丢附件，也能继续插入，回车用于换行。
- 图片支持悬停预览和点击固定。固定图片悬浮在输入区上方，关闭键在图片左上角按需出现，前后切换靠近图片；输入增高时图片适当缩小。
- 聚焦输入框时，Command+Z／Command+Y 在历史输入间前后切换。暂存草稿作为最新一项，修改旧输入后成为新草稿；草稿恢复不能覆盖用户刚输入的新内容。
- 运行中的后续消息有排队提示，可编辑、调序、删除及撤回到输入框，队列按对话隔离。
- 历史搜索覆盖标题和正文，可区分用户／模型，结合匹配方式、项目、模型、日期和归档范围。结果片段围绕命中字，跳转后有深浅主题均清楚的高亮。
- 对话导航使用紧凑无边框刻度，颜色表示当前阅读位置，可独立滚动，预览包含时间和对应输入／回复。
- 每轮末尾保留开始、最后回复与历时；运行中的对话、Goal或管家显示持续时间。新一轮不能抹掉上一轮记录，也不在顶栏长期占用一块静止时间区域。
- Token 可按本轮、本对话、模型和历史查看，并按日期、用途等筛选。轮次数字末尾用细线箭头展开；请求明细可看缓存、思考、可信计时和复制编号，当前筛选可完整导出 CSV/JSON。未知用量不当作零消耗，无实际起止的旧记录不伪造请求耗时。[用量记录说明](docs/usage-records-2026-11-02.md)。

锁屏空闲CPU样本由9.05%降至3.25%单核占用，内存样本未改善，不扩大为全部场景的性能收益。[测量与边界](docs/locked-idle-performance-2026-11-02.md)。

设计依据见[界面原则](docs/interface-design-principles.md)和[公开设计指导复审](docs/impeccable-interface-review-2026-11-01.md)。交互存在但尚未取得完整原生证据的项目，继续保留在验收清单中。

## 7. 开发、验证与交付约定

常用检查：

```bash
npm run typecheck
npm run test:all
npm run enigma:release-check
```

`test:all`依次运行宿主/界面与独立工程套件；只执行根目录`npm test`不覆盖工程套件。按改动范围先跑相关检查。只有新增改动、失败或尚未解决的疑点才扩大／重复验证；代码存在、接口成功和单测通过分别只是不同层面的证据。界面修改同时核对Web与桌面，原生能力必须实机验证。

本地打包入口是 `npm run enigma:pack`，会写入 `dist-enigma/`；先退出正在该目录运行的应用。打包需要匹配的 `HANA_SIGN_KEY` 与 `HANA_SIGN_KEYSET`，且公钥配置贯穿宿主和服务构建。密钥放在仓库外。本机验证使用 `SKIP_NOTARIZE=true` 和 `CSC_IDENTITY_AUTO_DISCOVERY=false` 时，仍须保留归档验签与本地签名检查；这不是生产公证。

- 保留用户和其他 Agent 的未提交修改；不重置或覆盖无关工作。
- 已验收迭代及时提交并推送，明确目标分支。更新`main`、合并、发布及启用GitHub Actions按明确授权处理，不从“push”推导额外操作。
- GitHub Actions当前保持关闭；Mac验收不以Windows环境或账单作为前置条件。
- 安装前备份应用与用户数据，核对模型、会话、草稿和附件；安装后检查应用、服务与界面实际版本。
- 构建产物、审计原始输入、密钥、配置和恢复备份放在仓库外或被忽略的产物目录，不进入提交或发行包。
- 仓库只记录本项目需求、实现、验收和公开技术来源，不纳入第三方私有源码、名称、内部链接、私有协议或提示词。公开版权、许可与实际复用声明必须保留。
- 不为精简而删掉用户要的能力。已经去除的重复统计界面、统一的CSV编辑与文件面板，以及保留可选能力的理由见[精简记录](docs/feature-consolidation-2026-11-01.md)。

## 8. 后续分析与创新方向

下表保留此前要求头脑风暴的点子。部分已有基础实现，但**列为方向不代表已完成，也不自动授权扩展为新的代码工程**。完成当前目标后，应提交依托届时现状的综合计划：具体场景、已有基础、还缺什么、收益证据、成本与优先级。

| 方向 | 希望解决的问题 | 下一步应证明什么 |
| --- | --- | --- |
| 行动前的失败经验提醒 | 换上下文后重复走刚失败的路线 | 在相同失败条件下及时提醒；条件变化后允许重试，降低重复无效操作 |
| 先证伪再投入 | 大规模修改后才发现接口、版本或入口判断错 | 用最小实验推翻关键假设；来源变化后重新检查 |
| 同起点方案与模型对照 | 不知道哪条路线或模型更适合 | 相同原成功标准下比较质量、总成本和耗时；保留放弃理由 |
| 验证分层与替代方法 | 验证过慢，任务长期得不到结论 | 更小检查减少等待，同时保留原验收条件，测量漏检风险 |
| 等待关系与终态渠道 | 看得到运行，却不知道在等谁、何时有结果 | 在等待前准备运行标识、结果查询和备用取证；解释缺来源与循环等待 |
| 最小范围恢复与任务改组 | 一个组件出错导致正确成果一起丢失 | 区分展示、观测、请求、工具、上下文与代码层恢复；保留有效成果并调整无效支线 |
| 跨仓契约与文档联动 | 接口变化后代码、说明、示例和记忆相互矛盾 | 找到受影响消费者与段落，真实运行例子，让独立任务照指南完成操作 |
| 差量交接与按需补读 | 复制全部历史昂贵，摘要又可能漏要求 | 携带必要背景、新目标、变化和来源索引，减少重复阅读而不丢约束 |
| 有价值的空闲整理 | 整理花钱却没被后续任务使用 | 用实际复用、错误和纠正反馈选择材料，计算整理加检索的总成本 |
| 外部事实保鲜 | 昨天有效的资料今天失效 | 按时效与版本复验，区分暂时失联与事实变化 |
| 决策回放与预算分配 | 看不懂为何选这条路，或干预是否值得 | 串起要求、假设、实验、失败、选中改动和验证；依据实际结果调整已授权模型与预算 |
| 广义管家的隔离维修 | 压缩、展示或观察链路坏了后无人处理 | 先复现和隔离修复，再按授权采用；避免重复副作用、无限监督和无约束自修改 |

优先围绕**跨仓改造及文档维护**形成小而完整的实际案例，衡量成功率、漏验、重复操作、交接遗漏、记忆有效性与总成本，不以新增面板数、代码行数或论文中的收益代替本项目效果。

继续保留必要的计划、独立验收、中断恢复、轻量记忆、中文召回、权限脱敏和按需审查。不引入强制每轮反思、固定多角色流水线、通用企业记忆平台或与当前任务无关的管理复杂度。
